Introdução

Crie o seu primeiro módulo sem ferramentas de compilação

Referência da API Baixar projeto de exemplo

Este documento é voltado para desenvolvedores de módulos e demonstra como criar do zero um aplicativo Web executado dentro do processo principal do yyzTools (tomando como exemplo o projeto de amostra do SDK, SDK_Sample — um localizador ultrarrápido de arquivos), cobrindo: estrutura de diretórios da página, janela hospedeira, i18n, Native API assíncrona (busca de arquivos em todo o disco), abertura de arquivos, persistência de configuração e, ainda, o modelo para adicionar novos métodos nativos quando for necessário estender as capacidades em C++.

A amostra é JS nativo puro, zero dependências de terceiros, sem build: não precisa de Vite / Alpine / FontAwesome; basta copiar os diretórios Web e Modules para o diretório do yyzTools.exe e ela já funciona.

1. Estrutura de diretórios da amostra e forma de implantação #

sdk/sample/
  Web/                        ← copiar para <diretório do yyzTools.exe>\Web\        (mesclar com o diretório Web existente)
    SDK_Sample/               ← diretório autossuficiente da amostra; a pasta inteira é um módulo completo
      index.html              # estrutura da página (DOM nativo, posições de texto marcadas com data-i18n)
      filefinder.js           # toda a lógica: busca / abrir / histórico / Esc
      filefinder.css          # estilos da página (tudo com variáveis --zen-*, adaptação automática a tema claro/escuro)
      i18n.js                 # dicionário de textos (zh_cn / en)
      lib/
        zen_api.js            # classe de encapsulamento ZenAPI (wrapper JS da Native API, única dependência de lib)
        window_controls.css   # variáveis de tema (--zen-*) + estilos da barra de controle da janela
  Modules/                    ← copiar para <diretório do yyzTools.exe>\Modules\    (mesclar com o diretório Modules existente)
    SDK_Sample.zenmod         # declaração de módulo type:"web"; o ModuleManager cria a janela hospedeira automaticamente

Implantação:

Copie/mescle sdk/sample/Web     em  bin64\Web\
Copie/mescle sdk/sample/Modules em  bin64\Modules\
Reinicie o yyzTools.exe e pesquise "SDK样例工程" no painel de comandos para iniciá-lo

Convenções dos locais lidos pelo programa principal:

Recurso Local
Página <exe目录>\Web\{page}\index.html
Módulo <exe目录>\Modules\<分类>\*.zenmod (varre apenas um nível de subdiretórios)

2. Visão geral da arquitetura: como um aplicativo Web é executado #

Modules/SDK_Sample.zenmod   ← arquivo de módulo que declara type:"web" (orientado a dados, sem precisar escrever C++)
        │  o programa principal varre os .zenmod na inicialização
        ▼
Janela hospedeira WebModule (janela nativa + WebView2)
        │  carrega Web\SDK_Sample\index.html
        ▼
Web/SDK_Sample/             ← todo o seu código front-end (JS nativo, zero dependências)
        │  window.Zen.xxx(...)  ←→  interfaces nativas registradas pelo programa principal
        ▼
Managers em C++ (arquivos / processos / janelas / área de transferência / OCR...)

Conclusões principais:

  • Não é preciso escrever nenhum código C++. Um .zenmod com type: "web" é automaticamente transformado pelo programa principal em uma janela hospedeira WebModule; tamanho da janela, ícone e nome multilíngue são todos declarados no arquivo do módulo.

  • O módulo obtém automaticamente: busca no painel de comandos (com índice pinyin), vinculação de atalhos globais, montagem no dock e registro na tabela de nomes do windowControl.

  • O único canal entre o front-end e o C++ é o window.Zen; chame sempre por meio da classe de encapsulamento ZenAPI (a amostra já inclui lib/zen_api.js).

  • As páginas sem build são arquivos estáticos; após editar, basta atualizar a janela para que tenham efeito (windowControl('sdk_sample','hide') e depois show, ou reiniciar o exe), sem nenhuma etapa de compilação.

3. Estrutura da página (JS nativo, quatro arquivos) #

index.html #

Não importa nenhuma biblioteca de terceiros; os três botões da barra de controle da janela usam caracteres Unicode como ícones (− / □ / ×), com estilos fornecidos por lib/window_controls.css. As posições de texto são marcadas com data-i18n / data-i18n-ph e preenchidas de uma vez na inicialização do JS. A estrutura tem quatro blocos: barra de busca, chips de histórico de buscas, barra de status (nº de resultados + dica de sintaxe) e lista de resultados:

<div class="search-bar">
    <input type="text" id="searchInput" class="search-input" data-i18n-ph="inputPlaceholder"
           spellcheck="false" autocomplete="off">
    <button class="search-btn" id="btnSearch" data-i18n="search"></button>
</div>
<div class="history-chips" id="historyChips"> ... </div>
<div class="status-bar">
    <span id="statusText" data-i18n="empty"></span>
    <span class="syntax-hint" data-i18n="syntaxHint"></span>
</div>
<div class="result-list" id="resultList"></div>

filefinder.js (lógica principal) #

Cinco responsabilidades; basta copiar tudo da amostra:

  1. Controle da janela: ZenAPI.windowControl('sdk_sample', 'min'|'max'|'close'|'drag'); o arrasto da barra de título só dispara quando o deslocamento passa de 5px; tecla Esc — se a caixa de entrada tem foco, primeiro blur; senão, fecha a janela.
  2. Tema: registra window.__applyTheme para receber o retorno do C++ (o data-theme da primeira tela é injetado pelo C++, não precisa de tratamento em JS).
  3. i18n: lê getConfig().language, obtém os textos do dicionário e preenche os elementos data-i18n; frases com placeholders {{count}} são expandidas por uma função de interpolação.
  4. Busca: searchFile(keyword, maxResults) é uma interface de vinculação assíncrona (executa em thread em segundo plano, não bloqueia a UI); Enter busca imediatamente e há debounce de 300ms na digitação para busca automática; usa números de série crescentes para descartar respostas fora de ordem — o lado nativo tem um mecanismo de "slot de busca" (uma nova requisição substitui diretamente a antiga ainda não concluída, e a Promise antiga recebe resultado vazio); o número de série no front-end evita que esse "resultado vazio que chega tarde" sobrescreva a renderização do novo resultado; os dois mecanismos trabalham juntos.
  5. Operações sobre resultados: openFile(fullPath, false) abre o arquivo (o duplo clique faz o mesmo; o segundo parâmetro é "executar como administrador"); openFileLocation(fullPath) abre o diretório que contém o arquivo; o caminho completo é montado com path + '\\' + name; o ícone usa diretamente o campo icon já presente no resultado (base64); o tamanho do arquivo é formatado com o campo numérico size.

Estrutura de retorno do searchFile ({ error, files[] }) #

Campos de cada item de files[]:

Campo Tipo Descrição
name / path string nome do arquivo / diretório em que está. Caminho completo = path + '\\' + name
dateModified string data de modificação (texto em formato localizado)
size número tamanho do arquivo em bytes, número nativo, use direto
icon string ícone em base64, consumível direto em <img src>, sem precisar chamar getFileIcon
score número pontuação de relevância (o nativo já ordena por pontuação)
isDir número 1/0 numérico, não booleano nativo (caminho de JSON montado à mão); teste com truthy ou === 1, nunca === true

Interfaces chamadas por esta amostra #

Interface Vinculação Finalidade
searchFile(keyword, maxResults) assíncrona busca pelo índice MFT de todo o disco, com suporte à sintaxe Everything (size:>100MB, ext:mp4, !ext:tmp)
openFile(path, admin) síncrona abre arquivo/diretório (comportamento padrão do shell); com admin=true executa como administrador
openFileLocation(path) síncrona localiza o arquivo no Explorador de Arquivos
getConfig(key?) síncrona lê a configuração: sem parâmetro retorna tudo; com key retorna só aquela chave (suporta caminho com pontos a.b)
setConfig(patch, replace?) síncrona gravação de granularidade estreita do histórico de buscas: setConfig({ sdk_sample: { history } }); replace=true substitui tudo (apenas para importar backup)
log(message) síncrona log do front-end, gravado no log do processo principal, facilitando diagnóstico
windowControl(name, action) síncrona minimizar/maximizar/fechar/arrastar a janela

Convenções de chamada (quatro regras de ouro) #

import ZenAPI from './lib/zen_api.js';

// 1. 判错用 isOk()（error 恒为数字：0 成功，-1 表示调用异常）
const res = await ZenAPI.searchFile('yyztools', 200);
if (!ZenAPI.isOk(res)) { ... }

// 2. 接口返回的布尔字段是原生布尔，直接判断
//    （例外一：config 的值由前端写入决定类型，通常是字符串，比较时注意归一）
//    （例外二：searchFile 结果的 isDir 是 1/0 数字——手拼 JSON 路径，用 truthy 或 === 1）
const ex = await ZenAPI.exists(path);
if (ex.exists === true) { ... }

// 3. 配置写入必须窄粒度，禁止全量回写
await ZenAPI.setConfig({ sdk_sample: { history } });   // 只写自己的键

// 4. 按 id 批量取应用信息用 getAppInfo，禁止循环 searchApp
const infos = await ZenAPI.getAppInfo(['calculator', 'ocr']);

As interfaces assíncronas (getAppInfo / searchFile / o quinteto de mídia / ocrRecognition) executam em thread em segundo plano; atenção: apenas um subprocesso de mídia roda por vez, e tarefas longas devem oferecer um ponto de cancelamento via cancelRun().

Consulta rápida de interfaces comuns (mais recursos além da amostra) #

Cenário Interface
Ler/gravar a própria configuração getConfig / setConfig (patch de granularidade estreita) / addConfig (anexa item a lista)
Abrir/salvar arquivos browseFile / browseDir / writeFile / readFile (>50MB usar readFileChunk)
Obter diretórios do sistema getKnownDir('download') etc.
Abrir página/programa externo runAny('https://...', '')
Copiar para a área de transferência navigator.clipboard do front-end (cenários de texto não precisam de native)

4. Criar o arquivo de módulo .zenmod (janela hospedeira) #

Crie um novo .zenmod em Modules/<分类>/ (arquivo da amostra: sdk/sample/Modules/SDK_Sample.zenmod):

{
    "id": "sdk_sample",
    "type": "web",
    "name": { "zh_cn": "SDK样例工程", "en": "SDK Sample Project", "...": "共 12 门语言" },
    "desc": { "zh_cn": "基于 MFT 索引的全盘急速文件搜索，支持 Everything 语法", "en": "..." },
    "icon": "fas fa-search",
    "winClassName": "yyzTools::SdkSampleWindowClass",
    "width": 760,
    "height": 540,
    "layoutType": 34,
    "url": "SDK_Sample/index.html",
    "preCreate": 0
}

Descrição dos campos (todos os campos lidos pelo programa principal quando type:"web"):

Campo Obrigatório Descrição
id Sim globalmente único. É também o nome da janela para windowControl/windowState, o appId de atalhos e o id de montagem no dock
type Sim fixo web
name Sim objeto com 12 idiomas; também aceita string pura (recomendado apenas para testes internos); fallback de valor: idioma atual → en → string pura
desc Não idem
icon Não classe FontAwesome (como acima) ou imagem em base64
winClassName Não nome da classe de janela Win32, basta ser globalmente único
width / height Não tamanho inicial da janela; padrão 800x600
layoutType Não máscara de bits do layout de posição inicial; 34 = centralizado horizontal + centralizado vertical
url Sim caminho da página relativo à raiz de Web (SDK_Sample/index.html); também aceita endereço online iniciado por http(s)
preCreate Não 1 = pré-cria a janela na inicialização (acelera a primeira abertura); padrão 0, cria sob demanda
canSuspend Não 1 = permite suspender o WebView quando a janela está oculta, poupando recursos (padrão 1)

Autoverificação ao terminar: JSON analisável, UTF-8 sem BOM, id globalmente único, todos os 12 idiomas não vazios.

Com isso o aplicativo está pronto — copie os dois diretórios conforme a seção 1 e pesquise "SDK样例工程" (Projeto de Amostra do SDK) ou "sdk" no painel de comandos para iniciá-lo (o índice pinyin é gerado automaticamente); windowControl('sdk_sample', 'show') também o invoca.

5. Textos multilíngues (por dicionário) #

A solução sem build usa um dicionário como ES module comum (i18n.js):

const messages = {
    zh_cn: { title: 'SDK样例工程', results: '{{count}} 个结果，耗时 {{ms}} ms', ... },
    en:    { title: 'SDK Sample Project', results: '{{count}} results in {{ms}} ms', ... }
};
export function getMessages(lang) { return messages[lang] || messages.en; }
export function interpolate(dict) {
    return (key, params) => { /* {{count}} → params.count */ };
}

Na inicialização, lê getConfig().language para escolher o idioma; se não encontrar, recua para en; frases com placeholders são expandidas com tf('results', { count, ms }).

Observações:

  • Os códigos de idioma usam o estilo sublinhado e minúsculo (zh_cn), igual ao .zenmod, não é BCP47.

  • O name/desc do .zenmod deve estar completo nos 12 idiomas; os textos dentro da página não têm exigência formal — a amostra traz só zh_cn/en; expanda conforme a necessidade.

  • Módulos que precisam trocar de idioma em tempo real junto com a interface podem transformar o dicionário em carregamento preguiçoso de arquivos multilíngues via import() sob demanda; o mecanismo é o mesmo deste documento.

6. Depuração e integração #

1. 免构建直接跑（推荐起步）：
   复制 sdk/sample/Web、sdk/sample/Modules 到 bin64\（Release exe 所在目录），重启 exe。
   改前端后 windowControl('sdk_sample','close') 再打开，或重启 exe 生效。

2. 浏览器看结构：
   直接双击 Web/SDK_Sample/index.html 用浏览器打开。
   浏览器里没有 window.Zen，ZenAPI.call 会走异常路径返回 error: -1，
   页面结构 / 样式 / 输入防抖 / 渲染逻辑均可正常调试（原生接口除外）。

Dica de desempenho da busca: searchFile usa o índice MFT de todo o disco no lado C++ e normalmente retorna em milissegundos; o nativo tem o mecanismo de slot de busca — uma nova requisição substitui a antiga não concluída (a antiga retorna resultado vazio); o front-end combina debounce de 300ms + número de série crescente para descartar respostas fora de ordem, de modo que digitação contínua não sobrecarrega a thread em segundo plano nem faz piscar resultados antigos. O ícone do resultado (base64) já vem de brinde no searchFile, sem precisar chamar getFileIcon à parte.

Quando as interfaces não forem suficientes (por exemplo, se for preciso uma nova capacidade em C++), registre a necessidade pelos canais de feedback do site oficial, para que o programa principal expanda as interfaces em versões futuras.

8. Avisos de segurança #

A Native API está totalmente aberta aos desenvolvedores de módulos quanto às capacidades do sistema do processo hospedeiro, incluindo leitura/gravação e exclusão de arquivos, criação e término de processos, controle de janelas, leitura/gravação da área de transferência, alteração de configurações do sistema, execução de linha de comando e outras operações de alto risco, sem diálogos de permissão, sem isolamento por sandbox e sem mecanismo de desfazer.

Antes de chamar, avalie por conta própria a segurança de cada operação: valide toda entrada externa, faça backup ou peça confirmação ao usuário antes de operações irreversíveis, e use apenas as capacidades de que a funcionalidade realmente precisa. Todas as consequências decorrentes são de responsabilidade do próprio desenvolvedor.
