Schnelleinstieg

Ihr erstes Modul — ganz ohne Build-Werkzeuge

API-Referenz Beispielprojekt herunterladen

Dieses Dokument richtet sich an Modulentwickler und zeigt, wie man von Grund auf eine Web-Anwendung erstellt, die im Hauptprozess von yyzTools läuft (am Beispiel des SDK-Beispielprojekts SDK_Sample – eines blitzschnellen Dateisuchers). Behandelt werden: Seitenverzeichnis, Fenster-Host, i18n, asynchrone Native API (Dateisuche auf der gesamten Festplatte), Öffnen von Dateien, Konfigurationspersistenz sowie die Vorlage zum Hinzufügen neuer nativer Methoden, wenn C++-Fähigkeiten erweitert werden müssen.

Das Beispiel ist reines natives JS, ohne Drittanbieter-Abhängigkeiten und build-frei: Vite / Alpine / FontAwesome werden nicht benötigt. Kopieren Sie einfach die beiden Verzeichnisse Web und Modules in das Verzeichnis von yyzTools.exe, und es läuft.

1. Beispielverzeichnis und Bereitstellung #

sdk/sample/
  Web/                        ← Kopieren nach <Verzeichnis von yyzTools.exe>\Web\        (mit vorhandenem Web-Verzeichnis zusammenführen)
    SDK_Sample/               ← eigenständiges Beispielverzeichnis, der gesamte Ordner ist ein vollständiges Modul
      index.html              # Seitenstruktur (natives DOM, Textpositionen mit data-i18n markiert)
      filefinder.js           # komplette Logik: Suche / Öffnen / Verlauf / Esc
      filefinder.css          # Seitenstil (durchgehend --zen-* Variablen, automatische Anpassung an hell/dunkel)
      i18n.js                 # Textwörterbuch (zh_cn / en)
      lib/
        zen_api.js            # ZenAPI-Klasse (JS-Wrapper der Native API, einzige lib-Abhängigkeit)
        window_controls.css   # Design-Variablen (--zen-*) + Stil der Fenstersteuerleiste
  Modules/                   ← Kopieren nach <Verzeichnis von yyzTools.exe>\Modules\    (mit vorhandenem Modules-Verzeichnis zusammenführen)
    SDK_Sample.zenmod         # Moduldeklaration type:"web", ModuleManager erstellt automatisch das Host-Fenster

Bereitstellung:

sdk/sample/Web     nach bin64\Web\ kopieren/zusammenführen
sdk/sample/Modules nach bin64\Modules\ kopieren/zusammenführen
yyzTools.exe neu starten, im Befehlspanel nach "SDK Sample Project" suchen und starten

Konventionen zu den Leseorten des Hauptprogramms:

Ressource Ort
Seite <exeVerzeichnis>\Web\{page}\index.html
Modul <exeVerzeichnis>\Modules\<Kategorie>\*.zenmod (nur eine Unterverzeichnisebene wird gescannt)

2. Architekturüberblick: Wie eine Web-Anwendung läuft #

Modules/SDK_Sample.zenmod   ← Moduldatei mit type:"web" (datengetrieben, kein C++ nötig)
        │  Hauptprogramm scannt .zenmod beim Start
        ▼
WebModule-Host-Fenster (natürliches Fenster + WebView2)
        │  lädt Web\SDK_Sample\index.html
        ▼
Web/SDK_Sample/             ← Ihr gesamter Frontend-Code (natives JS, null Abhängigkeiten)
        │  window.Zen.xxx(...)  ←→  vom Hauptprogramm registrierte native Schnittstellen
        ▼
C++-Manager (Dateien/Prozesse/Fenster/Zwischenablage/OCR...)

Wichtige Erkenntnisse:

  • Es muss kein C++-Code geschrieben werden. Eine .zenmod mit type: "web" wird vom Hauptprogramm automatisch als WebModule-Host-Fenster erstellt; Fenstergröße, Symbol und mehrsprachiger Name werden alle in der Moduldatei deklariert.

  • Das Modul erhält automatisch: Suche im Befehlspanel (inkl. Pinyin-Index), Bindung globaler Tastenkürzel, Andocken an das Dock, Registrierung in der windowControl-Namensliste.

  • Der einzige Kanal zwischen Frontend und C++ ist window.Zen; bitte rufen Sie alles einheitlich über die Wrapper-Klasse ZenAPI auf (das Beispiel enthält bereits lib/zen_api.js).

  • Build-freie Seiten sind direkt statische Dateien; nach Änderungen genügt ein Fenster-Refresh (windowControl('sdk_sample','hide') und dann show, oder exe neu starten), keinerlei Kompilierungsschritt.

3. Seitenstruktur (natives JS, vier Dateien) #

index.html #

Bindet keinerlei Drittanbieter-Bibliothek ein; die drei Buttons der Fenstersteuerleiste verwenden Unicode-Zeichen als Icons (− / □ / ×), der Stil wird von lib/window_controls.css geliefert. Textpositionen sind mit data-i18n / data-i18n-ph markiert und werden beim JS-Init einheitlich gefüllt. Die Struktur hat vier Blöcke: Suchleiste, Suchverlauf-Chips, Statusleiste (Ergebnisanzahl + Syntaxhinweis), Ergebnisliste:

<div class="search-bar">
    <input type="text" id="searchInput" class="search-input" data-i18n-ph="inputPlaceholder"
           spellcheck="false" autocomplete="off">
    <button class="search-btn" id="btnSearch" data-i18n="search"></button>
</div>
<div class="history-chips" id="historyChips"> ... </div>
<div class="status-bar">
    <span id="statusText" data-i18n="empty"></span>
    <span class="syntax-hint" data-i18n="syntaxHint"></span>
</div>
<div class="result-list" id="resultList"></div>

filefinder.js (Kernlogik) #

Fünf Verantwortlichkeiten, einfach vollständig aus dem Beispiel übernehmen:

  1. Fenstersteuerung: ZenAPI.windowControl('sdk_sample', 'min'|'max'|'close'|'drag'); Titelleisten-Drag wird erst bei Verschiebung über 5px ausgelöst; Esc-Taste – hat das Eingabefeld den Fokus, erst blur, sonst Fenster schließen.
  2. Design: Registrierung von window.__applyTheme zum Empfang der C++-Rückmeldung (data-theme beim ersten Screen wird von C++ injiziert, kein JS-Handling nötig).
  3. i18n: getConfig().language lesen, Texte aus dem Wörterbuch holen, alle data-i18n-Elemente durchlaufen und füllen; Sätze mit {{count}}-Platzhaltern werden mit einer Interpolationsfunktion expandiert.
  4. Suche: searchFile(keyword, maxResults) ist eine asynchron gebundene Schnittstelle (läuft im Hintergrundthread, blockiert die UI nicht); Enter sucht sofort, Eingabedebouncing 300ms sucht automatisch; mit aufsteigenden Sequenznummern werden außer Betrieb geratene Antworten verworfen – die native Seite hat einen Such-Slot-Mechanismus (eine neue Anfrage verdrängt direkt die alte, noch nicht abgeschlossene; das alte Promise erhält ein leeres Ergebnis), und die Frontend-Sequenznummer verhindert, dass dieses „spät eintreffende leere Ergebnis" das Rendern der neuen Ergebnisse überschreibt; beides greift ineinander.
  5. Ergebnisaktionen: openFile(fullPath, false) öffnet die Datei (Doppelklick genauso; zweiter Parameter = „mit Administratorrechten"); openFileLocation(fullPath) öffnet das übergeordnete Verzeichnis; der vollständige Pfad wird aus path + '\\' + name zusammengesetzt; das Icon wird direkt aus dem vorhandenen Feld icon (base64) im Ergebnis verwendet; die Dateigröße wird über das numerische Feld size formatiert angezeigt.

Rückgabestruktur von searchFile ({ error, files[] }) #

Felder der einzelnen Einträge in files[]:

Feld Typ Beschreibung
name / path Zeichenkette Dateiname / übergeordnetes Verzeichnis. Vollständiger Pfad = path + '\\' + name
dateModified Zeichenkette Änderungszeit (lokalisiertes Format)
size Zahl Dateigröße in Bytes, nativ, direkt verwendbar
icon Zeichenkette base64-Icon, direkt als <img src> nutzbar, kein erneuter Aufruf von getFileIcon nötig
score Zahl Relevanz-Score (native Seite hat bereits nach Score sortiert)
isDir Zahl 1/0 als Zahl statt nativer Boolean (handgezeichnetes JSON), Prüfung per truthy oder === 1, nicht === true

Schnittstellenübersicht der in diesem Beispiel aufgerufenen Funktionen #

Schnittstelle Bindung Zweck
searchFile(keyword, maxResults) asynchron MFT-Indexsuche auf der gesamten Festplatte, unterstützt Everything-Syntax (size:>100MB, ext:mp4, !ext:tmp)
openFile(path, admin) synchron Datei/Verzeichnis öffnen (Standard-Shell-Verhalten), bei admin=true mit Administratorrechten
openFileLocation(path) synchron Datei im Datei-Explorer lokalisieren
getConfig(key?) synchron Konfiguration lesen: ohne Argument alles, mit key nur dieser Schlüssel (unterstützt a.b-Punktpfad)
setConfig(patch, replace?) synchron Schmal granularen Suchverlauf schreiben: setConfig({ sdk_sample: { history } }); replace=true ersetzt alles (nur für Backup-Import)
log(message) synchron Frontend-Log, wird ins Hauptprozess-Log geschrieben, erleichtert die Fehlersuche
windowControl(name, action) synchron Fenster minimieren/maximieren/schließen/ziehen

Aufrufregeln (vier eiserne Regeln) #

import ZenAPI from './lib/zen_api.js';

// 1. 判错用 isOk()（error 恒为数字：0 成功，-1 表示调用异常）
const res = await ZenAPI.searchFile('yyztools', 200);
if (!ZenAPI.isOk(res)) { ... }

// 2. 接口返回的布尔字段是原生布尔，直接判断
//    （例外一：config 的值由前端写入决定类型，通常是字符串，比较时注意归一）
//    （例外二：searchFile 结果的 isDir 是 1/0 数字——手拼 JSON 路径，用 truthy 或 === 1）
const ex = await ZenAPI.exists(path);
if (ex.exists === true) { ... }

// 3. 配置写入必须窄粒度，禁止全量回写
await ZenAPI.setConfig({ sdk_sample: { history } });   // 只写自己的键

// 4. 按 id 批量取应用信息用 getAppInfo，禁止循环 searchApp
const infos = await ZenAPI.getAppInfo(['calculator', 'ocr']);

Asynchrone Schnittstellen (getAppInfo / searchFile / die fünf Medien-Runner / ocrRecognition) laufen in Hintergrundthreads. Beachten Sie, dass zu jedem Zeitpunkt nur ein Medien-Unterprozess läuft; langlaufende Aufgaben sollten eine Abbruchmöglichkeit über cancelRun() bieten.

Schnellreferenz häufiger Schnittstellen (weitere Fähigkeiten über das Beispiel hinaus) #

Szenario Schnittstelle
Eigene Konfiguration lesen/schreiben getConfig / setConfig (schmal granularer patch) / addConfig (Listenelement anhängen)
Datei öffnen/speichern browseFile / browseDir / writeFile / readFile (>50MB mit readFileChunk)
Systemverzeichnisse ermitteln getKnownDir('download') usw.
Webseite/externes Programm öffnen runAny('https://...', '')
In die Zwischenablage kopieren Frontend navigator.clipboard (für Text kein native nötig)
Screenshot/OCR screenCap('fast', ...) → ocrRecognition(base64) (beide asynchron)
Andere Modulfenster aufrufen windowControl('translate', 'show')

4. Erstellen der .zenmod-Moduldatei (Fenster-Host) #

Erstellen Sie unter Modules/<Kategorie>/ eine neue .zenmod (Beispieldatei: sdk/sample/Modules/SDK_Sample.zenmod):

{
    "id": "sdk_sample",
    "type": "web",
    "name": { "zh_cn": "SDK样例工程", "en": "SDK Sample Project", "...": "共 12 门语言" },
    "desc": { "zh_cn": "基于 MFT 索引的全盘急速文件搜索，支持 Everything 语法", "en": "..." },
    "icon": "fas fa-search",
    "winClassName": "yyzTools::SdkSampleWindowClass",
    "width": 760,
    "height": 540,
    "layoutType": 34,
    "url": "SDK_Sample/index.html",
    "preCreate": 0
}

Felderklärung (alle Felder, die das Hauptprogramm bei type:"web" liest):

Feld Pflicht Beschreibung
id Ja Global eindeutig. Zugleich Fenstername für windowControl/windowState, appId des Tastenkürzels, dock-Andock-id
type Ja Fixiert auf web
name Ja Objekt mit 12 Sprachen; reine Zeichenkette ebenfalls erlaubt (nur für interne Tests empfohlen); Rückfallkette: aktuelle Sprache → en → reine Zeichenkette
desc Nein wie oben
icon Nein FontAwesome-Klasse (wie oben) oder base64-Bild
winClassName Nein Win32-Fensterklassenname, muss nur global eindeutig sein
width / height Nein Initiale Fenstergröße, Standard 800x600
layoutType Nein Bitmaske für die initiale Positionsbestimmung, 34 = horizontal zentriert + vertikal zentriert
url Ja Seitenpfad relativ zum Web-Wurzelverzeichnis (SDK_Sample/index.html); Online-Adressen mit http(s)-Präfix werden ebenfalls unterstützt
preCreate Nein 1 = Fenster beim Start vorab erstellen (beschleunigt das erste Öffnen), Standard 0 = bei Bedarf erstellen
canSuspend Nein 1 = WebView darf beim Verstecken des Fensters suspendiert werden, um Ressourcen zu sparen (Standard 1)

Selbstprüfung nach Änderungen: JSON ist parsbar, UTF-8 ohne BOM, id global eindeutig, alle 12 Sprachen nicht leer.

Damit ist die Anwendung fertig – kopieren Sie die beiden Verzeichnisse wie in Abschnitt 1 beschrieben; die Suche nach „SDK Sample Project" oder „sdk" im Befehlspanel startet sie (der Pinyin-Index wird automatisch erzeugt), auch windowControl('sdk_sample', 'show') ruft sie auf.

5. Mehrsprachige Texte (Wörterbuch-Ansatz) #

Für die build-freie Lösung genügt ein gewöhnliches ES-Modul-Wörterbuch (i18n.js):

const messages = {
    zh_cn: { title: 'SDK样例工程', results: '{{count}} 个结果，耗时 {{ms}} ms', ... },
    en:    { title: 'SDK Sample Project', results: '{{count}} results in {{ms}} ms', ... }
};
export function getMessages(lang) { return messages[lang] || messages.en; }
export function interpolate(dict) {
    return (key, params) => { /* {{count}} → params.count */ };
}

Bei der Initialisierung Sprache über getConfig().language wählen, bei Fehlschlag Rückfall auf en; Sätze mit Platzhaltern werden über tf('results', { count, ms }) expandiert.

Hinweise:

  • Sprachcodes im Kleinbuchstaben-Stil mit Unterstrich (zh_cn), konsistent mit .zenmod, nicht BCP47.

  • Die name/desc der .zenmod müssen alle 12 Sprachen abdecken; für Texte innerhalb der Seite gilt keine Pflicht, das Beispiel liefert nur zh_cn/en – nach Bedarf erweitern.

  • Module, die der Oberflächensprache sofort folgen müssen, können das Wörterbuch per bedarfsgesteuertem import() als mehrsprachige Dateien lazy laden; der Mechanismus entspricht diesem Dokument.

6. Debugging und Integration #

1. Build-frei direkt ausführen (empfohlener Einstieg):
   sdk/sample/Web und sdk/sample/Modules nach bin64\ kopieren (Verzeichnis der Release-exe), exe neu starten.
   Nach Frontend-Änderungen windowControl('sdk_sample','close') und erneut öffnen, oder exe neu starten.

2. Struktur im Browser betrachten:
   Web/SDK_Sample/index.html einfach per Doppelklick im Browser öffnen.
   Im Browser gibt es kein window.Zen; ZenAPI.call geht den Ausnahmeweg und liefert error: -1,
   Seitenstruktur / Stile / Eingabe-Debouncing / Renderlogik lassen sich normal debuggen (nativ-gebundene Funktionen ausgenommen).

Hinweis zur Suchleistung: searchFile läuft über den MFT-Vollplatten-Index der C++-Seite und antwortet üblicherweise in Millisekunden; die native Seite hat einen Such-Slot-Mechanismus – eine neue Anfrage verdrängt die alte, noch nicht abgeschlossene (die alte liefert ein leeres Ergebnis), das Frontend kombiniert 300ms-Debouncing + aufsteigende Sequenznummern zum Verwerfen außer Betrieb geratener Antworten; selbst schnelles Tippen überlastet weder den Hintergrundthread noch flackern alte Ergebnisse. Ergebnis-Icons (base64) werden von searchFile gleich mitgeliefert, kein zusätzlicher getFileIcon-Aufruf nötig.

Reichen die Schnittstellenfähigkeiten nicht aus (z. B. wenn neue C++-Fähigkeiten nötig sind), können Sie Anforderungen über die Feedback-Kanäle der offiziellen Website einreichen; das Hauptprogramm erweitert die Schnittstellen in späteren Versionen.

8. Sicherheitshinweise #

Die Native API bietet Modulentwicklern vollständigen Zugriff auf die Systemfähigkeiten des Host-Prozesses, einschließlich Lesen/Schreiben/Löschen von Dateien, Erstellen und Beenden von Prozessen, Fenstersteuerung, Lesen/Schreiben der Zwischenablage, Änderung von Systemeinstellungen, Ausführung von Kommandozeilen und anderen hochriskanten Operationen – und zwar ohne Berechtigungsdialoge, ohne Sandbox-Isolation und ohne Rückgängig-Mechanismus.

Bewerten Sie vor jedem Aufruf selbst die Sicherheit jeder einzelnen Operation: Validieren Sie sämtliche externen Eingaben, erstellen Sie vor unwiderruflichen Operationen Backups oder holen Sie die Bestätigung des Benutzers ein, und nutzen Sie nur die Fähigkeiten, die Ihre Funktion wirklich benötigt. Sämtliche daraus entstehenden Folgen trägt der Entwickler selbst.
