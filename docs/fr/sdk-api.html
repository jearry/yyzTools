1. Conventions générales #

Ce document définit toutes les interfaces liées aux interactions avec le composant natif (Native) ; il couvre uniquement les interfaces enregistrées par le processus principal yyzTools.exe (SetupBindings() dans src/yyztools/NativeApi.cpp).

Mode d'appel #

  • Le front-end appelle les fonctions d'interface via l'objet window.Zen ; il est recommandé de passer systématiquement par la classe d'encapsulation ZenAPI : web/lib/zen_api.js, et non de se connecter directement à window.Zen dans le code métier, afin de servir de couche de compatibilité lors des évolutions des interfaces.

  • Entrées : transmises sous forme de paramètres positionnels ; le nombre et les types de paramètres dépendent de chaque interface

  • Sorties : transmises par valeur de retour, un objet json contenant les éléments suivants

    {
    "error": 0,
    "errorMsg": "",
    ...
}

    • error : 0 succès, non 0 erreur

    • errorMsg (optionnel) : message d'erreur

    • autres (optionnels) : voir chaque interface

Détection des erreurs #

error est toujours un nombre : 0 succès, non 0 erreur (-1 en cas d'exception d'appel).

Liaison synchrone / asynchrone #

La grande majorité des interfaces sont des liaisons synchrones (BindSync) : l'appel retourne immédiatement. Les 7 interfaces suivantes sont des liaisons asynchrones (BindAsync), exécutées dans un thread d'arrière-plan, qui reviennent via une Promise sans bloquer le thread UI :

getAppInfo, searchFile, imageRun, ffmpegRun, pdfRun, gsRun, ocrRecognition

Les contraintes de comportement des interfaces asynchrones à un instant donné sont décrites dans chaque entrée (par exemple, le quintette média s'exécute en série et partage cancelRun pour l'annulation).

1. Obtenir la version du client #

function Zen.getVersion() : object

  • Entrées : aucune

  • Sorties

    {
    "error": 0,
    "errorMsg": "",
    "apiVersion": "1.0.1",
    "appVersion": "1.0.1",
    "usageTime": 90,
    "usageTimes": 3602,
    "firstUseTime": "20250910"
}

    • apiVersion : informations de version de l'API client. Le numéro s'incrémente de 1 à chaque mise à jour des interfaces ; le dernier chiffre va de 0 à 9 puis repart à 0, par exemple 1.0.0, 1.0.1, 1.0.2... 1.0.9, 1.1.0, etc.

    • appVersion : informations de version du client

    • usageTime : temps d'utilisation (unité : s)

    • usageTimes : nombre d'activations

    • firstUseTime : date de première utilisation, format : yyyymmdd

2. Obtenir la configuration #

function Zen.getConfig(key?: string) : object

  • Entrées

    • key (optionnel) : ne retourne que cette clé ; les chemins en points a.b sont pris en charge. Par défaut, retourne la configuration complète.

      • clé trouvée : retourne {"error":0, "<key>": <valeur>}, par exemple getConfig("language") → {"error":0,"language":"zh_cn"} ; getConfig("dock.categories") → {"error":0,"dock":{"categories":[...]}}

      • clé absente : retourne {"error":0} (pas d'erreur ; le lecteur doit gérer le repli)

  • Sorties (exemple, les champs dépendent de la configuration réelle)

    {
    "error": 0,
    "errorMsg": "",
    "logLevel": "1",
    "wallpaperEnabled": "1",
    "overlayEnabled": "0",
    "gameMode": "0",
    "clipboardHistoryMaxCount": "500",
    "autoStart": "1",
    "shortcutKeys": {
        "main": {
            "doubleCtrlEnabled": "1",
            "doubleAltEnabled": "1",
            "modifier": 1,
            "virtualCode": 32
        },
        "apps": [
            {
                "appId": "translate",
                "modifier": 1,
                "virtualCode": 49
            },
            {
                "appId": "ocr",
                "modifier": 1,
                "virtualCode": 50
            }
        ]
    },
    "quickOpen": [
        {
            "name": "谷歌搜索",
            "type": "normal",
            "index": "0",
            "url": "https://www.google.com/search?q={query}",
            "enabled": "1"
        }
    ],
    "customApps": [
        {
            "filePath": "d:\test\test1.exe",
            "enabled": "1"
        }
    ]
}

    • logLevel : niveau de journalisation (0 : Trace / 1 : Debug / 2 : Info / 3 : Warning / 4 : Error / 5 : Fatal)

    • wallpaperEnabled : activer le fond d'écran dynamique

    • overlayEnabled : activer les effets de bureau

    • gameMode : mode jeu

    • clipboardHistoryMaxCount : nombre maximal d'entrées dans l'historique du presse-papiers

    • autoStart : démarrage automatique au lancement du système

    • shortcutKeys : raccourcis globaux

      • main : interface principale

        • doubleCtrlEnabled : réveil par double Ctrl

        • doubleAltEnabled : réveil par double Alt

        • modifier : touche modificatrice

        • virtualCode : touche principale

      • apps : applications

        • appId : id de l'application

        • modifier : touche modificatrice

        • virtualCode : touche principale

    • quickOpen : ouverture rapide

      • name : nom

      • type : type (normal : recherche générale / spec : recherche verticale)

      • index : numéro d'ordre

      • url : modèle d'url

      • enabled : activé ou non

    • customApps : applications personnalisées

      • filePath : chemin de l'exe correspondant à l'application

      • enabled : activé ou non

    • dock : dock (catégories + contenus)

      • Convention générale : l'absence de name/icon signifie « utiliser les valeurs intégrées par défaut » (dérivées à l'exécution par l'i18n ou par le .zenmod correspondant à appId, varient selon la langue de l'interface) ; la présence de ces champs signifie une personnalisation utilisateur, affichée telle quelle sans re-traduction.**

      • categories : catégories

        • id : les catégories intégrées utilisent des id sémantiques (folder/tools/ai/game/system), les créations utilisateur utilisent category_<horodatage>

        • name : optionnel, présent uniquement après renommage par l'utilisateur

        • icon : classe FontAwesome

        • color : couleur de thème

        • order : ordre de tri

      • contents : éléments de contenu

        • id : les éléments de répertoires intégrés utilisent des id sémantiques (desktop/documents/downloads/music/videos), les autres sont content_<horodatage>

        • categoryId : id de la catégorie de rattachement

        • type : app | folder | url

        • appId : obligatoire si type=app, correspond à l'id du .zenmod ; le nom et l'icône en sont tous deux dérivés, ne pas persister

        • folderPath : obligatoire si type=folder, prend en charge les variables d'environnement telles que %USERPROFILE%

        • url : obligatoire si type=url, URL complète normalisée (le préfixe https:// est ajouté automatiquement si absent) ; au clic, ouverture par le navigateur par défaut du système. Le nom est saisi par l'utilisateur, l'icône est récupérée à l'exécution via le favicon du site (repli fas fa-globe en cas d'échec), non persistée

        • name / icon : optionnels, sémantique identique ci-dessus (obligatoires pour les répertoires choisis par l'utilisateur en type=folder)

        • color : teinte de l'icône

        • order : ordre de tri au sein de la même catégorie

3. Modifier la configuration #

function Zen.setConfig(config: json_obj, replace?: boolean) : object

  • Entrées

    • config : identique à getConfig

      • ne transmettre que ce qui doit être modifié, pas besoin de tout transmettre

      • le contenu sous une même clé doit être transmis en entier

      {
    "logLevel": "1"
}

    • replace (optionnel, false par défaut) : false = fusion incrémentale dans la configuration existante, true = remplacement intégral (pour l'import de sauvegarde, permet de nettoyer les éléments de liste supprimés). Transmettre les chaînes "true" ou "false", l'absence équivaut à "false".

  • Remarque : ne pas « lire toute la configuration avec getConfig puis la réécrire en entier avec setConfig » — la valeur retournée par getConfig contient le champ error, et une réécriture intégrale le persiste dans le fichier de configuration. Toujours écrire à granularité étroite, par ex. setConfig({ dock: { categories } }).

  • Sorties

    {
    "error": 0,
    "errorMsg": ""
}

3. Obtenir l'état d'une fenêtre #

function Zen.windowState(window: string, can_suspend?: boolean) : object

  • Entrées

    • window : Name ou forme string du HWND, voir contrôle des fenêtres

    • can_suspend (optionnel) : autoriser la suspension du WebView de cette fenêtre (interrupteur de gestion des ressources, false par défaut)

2. Obtenir des informations d'applications en lot par id (asynchrone) #

function Zen.getAppInfo(appIds: string[]) : object

La configuration ne persiste que appId ; nom et icône sont dérivés à l'exécution (le name du .zenmod est multilingue ; un instantané dans la configuration deviendrait obsolète après un changement de langue). C'est précisément à ce scénario que cette interface est destinée.

⚠️ Ne pas la remplacer par une boucle de searchApp(appId, 1) : chaque searchApp effectue un balayage complet de l'index des applications + correspondance pinyin + tri par score, lance en outre deux threads concurrents et retourne plusieurs résultats avec icônes base64. Le dock plus les raccourcis comptent des dizaines d'appId ; les interroger un par un ralentirait nettement le démarrage. Cette interface les récupère en un seul appel ; côté native, résolution exacte par map::find.

Elle attend en interne que l'index des applications soit prêt (index généré par un thread d'arrière-plan) ; c'est donc une liaison asynchrone, et un appel au tout début d'un démarrage à froid ne retournera pas de résultat vide.

  • Entrées

    • appIds : tableau d'appId, ex. ["calculator", "Microsoft.WindowsCamera"]

  • Sorties

    Format strictement identique à searchApp (même BuildAppResult), sauf que :

    • seuls les éléments trouvés exactement sont retournés ; les id introuvables sont silencieusement ignorés, si bien que apps.length peut être inférieur à la longueur d'entrée (utile pour détecter des appId invalides dans la configuration)

    • l'ordre suit celui des paramètres d'entrée, score vaut toujours 0 (non soumis au scoring)

    {
    "error": 0,
    "apps": [
        {
            "id": "calculator",
            "name": "超级计算器",
            "path": "calculator",
            "desc": "",
            "icon": "data:image/png;base64,",
            "appType": 4,
            "score": 0
        }
    ]
}

  • Description : la recherche est exécutée par le service maison yyzFileSearch (index MFT + IPC par canal nommé) ; la syntaxe de requête style Everything est prise en charge (ex. size:>100MB, !ext:mp4), résultats triés par pertinence. La recherche s'exécute dans un thread d'arrière-plan : liaison asynchrone.

  • Entrées

    • keyword : mot-clé de recherche

    • maxResults : nombre maximal d'enregistrements

  • Sorties

    {
  "error": 0,
  "files": [
    {
      "name": "WinMain.cpp",
      "path": "D:\\WorkCodeup\\yyztools\\src\\yyztools",
      "dateModified": "2025/10/18 14:05:00",
      "icon": "data:image/png;base64,",
      "score": 0,
      "isDir": 0
    }
  ]
}

    • files : liste des fichiers

      • name : nom du fichier

      • path : répertoire contenant le fichier (sans le nom de fichier), chemin complet = path + "\" + name

      • dateModified : date de modification

      • icon : icône du fichier, format base64

      • score : score de recherche

      • isDir : 1 signifie répertoire, 0 signifie fichier

7. Traitement multimédia #

Le quintette média fait appel, côté C++, à des outils CLI tiers situés sous bin64\Platform\. Tous, sauf ffprobeRun, sont des liaisons asynchrones (exécution dans un thread d'arrière-plan, sans blocage du thread UI) ; les traitements par lot sont sériels, un seul sous-processus s'exécute à la fois, et Zen.cancelRun() permet d'interrompre l'exécution en cours (en cas d'annulation, retour de errorMsg: "cancelled").

1. Exécuter une commande magick (asynchrone) #

function Zen.imageRun(args: string) : object

  • Entrées

    • args : arguments complets de la ligne de commande magick (magick.exe lui-même exclu), assemblés par le front-end. Les chemins doivent être entourés de guillemets doubles, par exemple "D:\\in.jpg" -resize 800x600 "D:\\out.jpg"

  • Sorties

    {
  "error": 0,
  "stdout": "..."
}

  • Remarque : le côté C++ n'assemble pas les arguments, il exécute simplement magick.exe <args> et capture le résultat. Si error est non 0, errorMsg transmet le stderr de magick ; stdout est la sortie standard de magick (résultat des commandes identify, etc.)

9. Chiffrement et déchiffrement #

1. Chiffrer des données #

function Zen.encrypt(target: string, algorithm: string, type: string, key: string, iv: string) : object

  • Entrées

    • target : données à chiffrer

      • si type="text" : chaîne de texte

      • si type="data" : données binaires encodées en Base64

      • si type="hex" : chaîne hexadécimale

      • si type="file" : chemin de fichier

    • algorithm : algorithme de chiffrement

      • chiffrement symétrique : "aes-128-cbc", "aes-192-cbc", "aes-256-cbc", "aes-128-ecb", "aes-256-ecb", "aes-128-ctr", "aes-256-ctr", "des-cbc", "des-ecb", "des-ede3-cbc" (3DES), "des-ede3-ecb", "rc4", "bf-ecb" (Blowfish), "rc2-cbc", "sm4-cbc", "sm4-ecb", "sm4-ctr"

      • chiffrement asymétrique : "rsa-pkcs1", "rsa-oaep" (RSA, chiffrement par clé publique, déchiffrement par clé privée), "sm2" (courbe elliptique nationales sm2p256v1, chiffrement par clé publique, déchiffrement par clé privée ; traite des données de longueur quelconque en une seule passe, sans découpage)

      • key/iv en Base64 ; convertis en interne en hexadécimal puis transmis sous la forme enc -K <hex> -iv <hex>, la longueur de clé doit correspondre exactement à l'algorithme

    • type : type d'entrée (par défaut "text")

      • "text" : données textuelles

      • "data" : données binaires encodées en Base64

      • "hex" : chaîne hexadécimale

      • "file" : chemin de fichier

    • key : pour le symétrique, clé encodée en Base64 ; pour l'asymétrique (rsa-*, sm2), texte PEM (clé publique pour chiffrer, clé privée pour déchiffrer ; transmise telle quelle, sans décodage Base64)

    • iv : vecteur d'initialisation encodé en Base64 (optionnel, requis par certains algorithmes ; ignoré en asymétrique)

  • Sorties

    {
  "error": 0,
  "result": "Base64编码的加密数据",
  "algorithm": "aes-256-cbc",
  "type": "text",
  "inputSize": 1024,
  "outputSize": 1040
}

3. Générer une clé #

function Zen.generateKey(algorithm: string, bits: string = '') : object

Point d'entrée unifié de génération de clés (générées par le openssl.exe intégré, le front-end n'a pas besoin de dépendre du WebCrypto du navigateur).

  • Entrées

    • algorithm : nom de l'algorithme

      • symétrique : aes-128-cbc / aes-256-cbc / des-cbc / des-ede3-cbc / sm4-cbc / sm4-ecb / sm4-ctr / rc2-cbc / rc4 / bf-ecb, etc. (longueur de clé déduite du nom de l'algorithme)

      • asymétrique : "rsa" (bits est effectif) / "sm2" (courbe fixe sm2p256v1)

    • bits : taille de la clé RSA ("2048"/"4096", 2048 par défaut) ; ignorée pour les algorithmes symétriques et SM2

  • Sorties

    // 对称算法
{ "error": 0, "algorithm": "aes-256-cbc", "key": "Base64编码的密钥" }
// 非对称算法
{ "error": 0, "algorithm": "sm2", "publicKey": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n", "privateKey": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n" }

4. Générer un IV #

function Zen.generateIv(algorithm: string) : object

Génère un IV aléatoire selon la taille de bloc de l'algorithme symétrique (généré par le openssl.exe intégré).

  • Entrées

    • algorithm : nom de l'algorithme symétrique (même liste que les algorithmes symétriques de encrypt)

  • Sorties

    { "error": 0, "algorithm": "aes-256-cbc", "iv": "Base64编码的IV" }

    Remarque : taille de bloc AES/SM4 : 16 octets ; DES/3DES/RC2 : 8 octets ; le mode ECB et les chiffrements de flux (rc4) n'ont pas besoin d'IV, iv retourne une chaîne vide.

5. Calculer un hash #

function Zen.calcHash(target: string, algorithm: string, type?: string, key?: string) : object

  • Entrées

    • target : cible du calcul, dont le sens varie selon type

      • si type="file" : chemin de fichier

      • si type="text" : chaîne de texte (empreinte calculée en UTF-8)

      • si type="data" : données binaires encodées en Base64

      • si type="hex" : chaîne hexadécimale

    • algorithm : algorithme de hachage

      • "md5"

      • "sha1"

      • "sha224"

      • "sha256"

      • "sha384"

      • "sha512"

      • "ripemd160"

      • "sm3" (empreinte SM3 nationales, 256 bits / 64 chiffres hexadécimaux)

      • "sha3-224" / "sha3-256" / "sha3-384" / "sha3-512" (SHA-3 / Keccak, NIST FIPS 202)

      • "blake2b512" / "blake2s256" (BLAKE2, empreintes modernes haute performance)

      • "crc32" (somme de contrôle CRC32, 8 chiffres hexadécimaux)

      • "crc16" (somme de contrôle CRC16, 4 chiffres hexadécimaux)

      • "checksum" (somme cumulée des octets, 8 chiffres hexadécimaux)

      • "hmac-md5" / "hmac-sha1" / "hmac-sha256" / "hmac-sha512" / "hmac-sm3" / "hmac-sha3-256" / "hmac-sha3-512" (HMAC ; le 4e paramètre key est la clé, sortie MAC en hexadécimal)

    • type : type d'entrée (optionnel, "file" par défaut)

      • "file" : calculer le hash d'un fichier

      • "text" : calculer le hash d'un texte

      • "data" : calculer le hash de données binaires (target doit être une chaîne Base64)

      • "hex" : calculer le hash d'une chaîne hexadécimale (target est une chaîne hexadécimale, décodée puis calculée par octets)

  • Sorties

    {
  "error": 0,
  "hash": "D41D8CD98F00B204E9800998ECF8427E",
  "algorithm": "md5",
  "type": "file"
}

13. Mise à jour #

La mise à jour est assurée par un processus distinct, yyzUpdater.exe ; le processus principal se contente de le lancer et de sonder son état.

1. Vérifier les mises à jour #

function Zen.checkUpdate() : object

Lance yyzUpdater.exe --check-and-apply (détection + téléchargement + application, tout en un).

  • Entrées : aucune

  • Sorties

    { "error": 0, "errorMsg": "success" }

    Remarque : error:0 signifie seulement que le programme de mise à jour a été lancé avec succès, pas le résultat de la mise à jour. L'état de progression/de disponibilité s'interroge via getUpdateState.

2. Obtenir l'état de la mise à jour #

function Zen.getUpdateState() : object

Sonde en temps réel l'état de la mise à jour (pour l'interrogation par la zone de notification) :

  • l'updater s'exécute-t-il → mutex à instance unique Local\yyzUpdater_SingleInstance

  • un téléchargement est-il prêt à être appliqué → existence de %APPDATA%\yyzTools\Update\update.ready (si présent, analyse de la version du paquet main qu'il contient)

  • une vérification manuelle est-elle terminée sans mise à jour → marqueur %APPDATA%\yyzTools\Update\update.result (lu puis supprimé)

  • Entrées : aucune

  • Sorties

    { "error": 0, "status": "idle", "version": "", "lastResult": "" }

    • status : idle (aucune activité de mise à jour) / checking (programme de mise à jour en cours) / ready (téléchargement terminé, mise à niveau possible)

    • version : renseigné uniquement en état ready, numéro de la nouvelle version à appliquer (paquet main) ; chaîne vide sinon

    • lastResult : renseigné uniquement en état idle, résultat de la dernière vérification manuelle (--check-and-apply) : uptodate (déjà à jour) / error (échec de la vérification) ; chaîne vide sans marqueur. Ce marqueur est écrit par l'updater et supprimé immédiatement après lecture par cette interface : il n'est donc retourné qu'une seule fois, pour qu'un seul Toast côté front ; le --check silencieux n'écrit pas de marqueur et ne produit aucune notification.

    • Priorité des états : checking > ready > idle

3. Appliquer une mise à jour déjà téléchargée #

function Zen.applyUpdate() : object

Lance yyzUpdater.exe --apply : lecture de update.ready → attente de la sortie du processus principal → remplacement des fichiers → redémarrage du processus principal. À appeler uniquement quand getUpdateState retourne ready.

  • Entrées : aucune

  • Sorties

    { "error": 0, "errorMsg": "success" }

⚠️ Consignes de sécurité #

L'API native expose aux développeurs de modules l'intégralité, sans restriction, des capacités système du processus hôte, y compris des opérations à haut risque telles que la lecture/écriture et la suppression de fichiers, la création et l'arrêt de processus, le contrôle de fenêtres, la lecture/écriture du presse-papiers, la modification du registre et des réglages système, le téléchargement réseau et l'exécution de commandes.

Ces interfaces n'ont pas de boîte de dialogue de permissions, pas d'isolation en bac à sable (sandbox), pas de mécanisme d'annulation — un appel prend effet immédiatement avec les droits de l'utilisateur courant ; un usage erroné peut entraîner une perte de données définitive ou un dysfonctionnement du système.

Par conséquent, veillez impérativement à :

  • Évaluer vous-même la sécurité : avant d'appeler une interface, assurez-vous que les paramètres (notamment les chemins, les noms de processus, les lignes de commande) proviennent de sources fiables et sont suffisamment validés ; pour les opérations irréversibles telles que la suppression, l'écrasement ou l'arrêt d'un processus, une sauvegarde préalable ou une confirmation auprès de l'utilisateur est recommandée.
  • Se méfier des entrées non fiables : n'injectez jamais directement, sans validation, des entrées utilisateur, des réponses réseau ou des données tierces dans les paramètres d'interface ; méfiez-vous du path traversal et de l'injection de commandes.
  • Principe du moindre privilège : ne demandez que les capacités réellement nécessaires à votre activité, évitez par facilité des interfaces au périmètre d'impact plus large.
  • Responsabilité personnelle : le développeur assume l'entière responsabilité de toutes les conséquences résultant de l'utilisation de cette API, y compris mais sans s'y limiter : perte de données, dommages système et risques de sécurité.
