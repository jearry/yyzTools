Démarrage rapide

Créez votre premier module sans aucun outil de build

Référence de l’API Télécharger le projet d’exemple

Cet article s'adresse aux développeurs de modules et montre comment créer de zéro une application Web s'exécutant dans le processus principal de yyzTools (en prenant pour exemple le projet d'échantillon SDK SDK_Sample — un chercheur de fichiers ultra-rapide). Il couvre : la structure des répertoires de la page, la fenêtre hôte, l'i18n, l'API native asynchrone (recherche de fichiers sur tout le disque), l'ouverture de fichiers, la persistance de la configuration, ainsi que le modèle d'ajout d'une méthode native lorsqu'il faut étendre les capacités C++.

L'échantillon est en JS purement natif, sans aucune dépendance tierce et sans build : pas besoin de Vite / Alpine / FontAwesome, il suffit de copier les deux répertoires Web et Modules dans le répertoire de yyzTools.exe pour l'exécuter.

1. Structure du répertoire de l'échantillon et mode de déploiement #

sdk/sample/
  Web/                        ← copier vers <répertoire de yyzTools.exe>\Web\        (fusion avec le répertoire Web existant)
    SDK_Sample/               ← répertoire auto-contenu de l'échantillon ; le dossier entier constitue un module complet
      index.html              # structure de la page (DOM natif, emplacements de texte marqués par data-i18n)
      filefinder.js           # toute la logique : recherche / ouverture / historique / Échap
      filefinder.css          # styles de la page (uniquement des variables --zen-*, s'adapte automatiquement au mode clair/sombre)
      i18n.js                 # dictionnaire de textes (zh_cn / en)
      lib/
        zen_api.js            # classe d'encapsulation ZenAPI (wrapper JS de l'API native, seule dépendance lib)
        window_controls.css   # variables de thème (--zen-*) + styles de la barre de contrôle de fenêtre
  Modules/                   ← copier vers <répertoire de yyzTools.exe>\Modules\    (fusion avec le répertoire Modules existant)
    SDK_Sample.zenmod         # déclaration de module type:"web", ModuleManager crée automatiquement la fenêtre hôte

Déploiement :

Copier/fusionner sdk/sample/Web     vers  bin64\Web\
Copier/fusionner sdk/sample/Modules vers  bin64\Modules\
Redémarrer yyzTools.exe, chercher « SDK样例工程 » dans le panneau de commandes pour le lancer

Convention des emplacements lus par le programme principal :

Ressource Emplacement
Page <répertoire exe>\Web\{page}\index.html
Module <répertoire exe>\Modules\<catégorie>\*.zenmod (un seul niveau de sous-répertoires analysé)

2. Vue d'ensemble de l'architecture : comment une application Web s'exécute #

Modules/SDK_Sample.zenmod   ← fichier de module déclarant type:"web" (piloté par les données, sans C++ à écrire)
        │  analysé par le programme principal au démarrage (.zenmod)
        ▼
Fenêtre hôte WebModule (fenêtre native + WebView2)
        │  charge Web\SDK_Sample\index.html
        ▼
Web/SDK_Sample/             ← tout votre code front-end (JS natif, zéro dépendance)
        │  window.Zen.xxx(...)  ←→  interfaces natives enregistrées par le programme principal
        ▼
Managers C++ (fichiers / processus / fenêtres / presse-papiers / OCR...)

Conclusions clés :

  • Aucun code C++ à écrire. Un .zenmod de type: "web" est automatiquement transformé par le programme principal en fenêtre hôte WebModule ; la taille de la fenêtre, l'icône et le nom multilingue sont tous déclarés dans le fichier de module.

  • Le module obtient automatiquement : la recherche dans le panneau de commandes (avec index pinyin), la liaison de raccourcis globaux, le montage dans le dock, l'enregistrement dans la table des noms windowControl.

  • Le seul canal entre le front-end et le C++ est window.Zen ; passez systématiquement par la classe d'encapsulation ZenAPI (l'échantillon inclut déjà lib/zen_api.js).

  • Une page sans build est directement un fichier statique : après modification, il suffit de rafraîchir la fenêtre (windowControl('sdk_sample','hide') puis show, ou redémarrer l'exe), sans aucune étape de compilation.

3. Structure de la page (JS natif, quatre fichiers) #

index.html #

N'inclut aucune bibliothèque tierce ; les trois boutons de la barre de contrôle de fenêtre utilisent des caractères Unicode comme icônes (− / □ / ×), stylés par lib/window_controls.css. Les emplacements de texte sont marqués par data-i18n / data-i18n-ph et remplis en bloc à l'initialisation du JS. La structure comporte quatre blocs : barre de recherche, chips d'historique de recherche, barre d'état (nombre de résultats + aide syntaxique), liste de résultats :

<div class="search-bar">
    <input type="text" id="searchInput" class="search-input" data-i18n-ph="inputPlaceholder"
           spellcheck="false" autocomplete="off">
    <button class="search-btn" id="btnSearch" data-i18n="search"></button>
</div>
<div class="history-chips" id="historyChips"> ... </div>
<div class="status-bar">
    <span id="statusText" data-i18n="empty"></span>
    <span class="syntax-hint" data-i18n="syntaxHint"></span>
</div>
<div class="result-list" id="resultList"></div>

filefinder.js (logique centrale) #

Cinq responsabilités, qu'il suffit de reprendre telles quelles de l'échantillon :

  1. Contrôle de fenêtre : ZenAPI.windowControl('sdk_sample', 'min'|'max'|'close'|'drag') ; le déplacement de la barre de titre ne se déclenche que si le déplacement dépasse 5px ; touche Échap — si la zone de saisie a le focus, blur d'abord, sinon fermer la fenêtre.
  2. Thème : enregistrer window.__applyTheme pour recevoir les notifications du C++ (le data-theme initial est injecté par le C++, aucun traitement JS nécessaire).
  3. i18n : lire getConfig().language, récupérer les textes du dictionnaire et remplir tous les éléments data-i18n ; les phrases avec des espaces réservés {{count}} sont développées par une fonction d'interpolation.
  4. Recherche : searchFile(keyword, maxResults) est une interface liée de façon asynchrone (exécutée dans un thread d'arrière-plan, ne bloque pas l'UI) ; recherche immédiate sur Entrée, recherche automatique avec anti-rebond de 300ms à la saisie ; un numéro croissant permet d'écarter les réponses en désordre — le côté native dispose d'un mécanisme de « slot » de recherche (une nouvelle requête évince directement l'ancienne non terminée, l'ancienne Promise recevant un résultat vide) ; le numéro côté front empêche cet « arrivée tardive d'un résultat vide » d'écraser le rendu du nouveau résultat, les deux se complétant.
  5. Opérations sur les résultats : openFile(fullPath, false) ouvre le fichier (idem au double-clic ; le second paramètre signifie « droits administrateur ») ; openFileLocation(fullPath) ouvre le répertoire parent ; le chemin complet est construit par path + '\\' + name ; l'icône utilise directement le champ icon déjà présent dans le résultat (base64) ; la taille du fichier est affichée formatée à partir du champ numérique size.

Structure de retour de searchFile ({ error, files[] }) #

Champs de chaque élément de files[] :

Champ Type Description
name / path chaîne nom du fichier / répertoire parent. Chemin complet = path + '\\' + name
dateModified chaîne date de modification (texte au format localisé)
size nombre taille du fichier en octets, nombre natif à utiliser directement
icon chaîne icône base64, utilisable directement dans <img src>, sans rappeler getFileIcon
score nombre score de pertinence (déjà trié par score côté native)
isDir nombre 1/0 en nombre et non en booléen natif (chemin JSON assemblé à la main), tester avec truthy ou === 1, pas === true

Interfaces appelées par cet échantillon #

Interface Liaison Usage
searchFile(keyword, maxResults) asynchrone recherche via l'index MFT de tout le disque, syntaxe style Everything (size:>100MB, ext:mp4, !ext:tmp)
openFile(path, admin) synchrone ouvre le fichier/répertoire (comportement shell par défaut), avec droits administrateur si admin=true
openFileLocation(path) synchrone localise le fichier dans l'Explorateur
getConfig(key?) synchrone lecture de la configuration : tout par défaut, uniquement la clé si key fourni (chemin en points a.b pris en charge)
setConfig(patch, replace?) synchrone écriture à granularité étroite de l'historique de recherche : setConfig({ sdk_sample: { history } }) ; replace=true remplace tout (import de sauvegarde uniquement)
log(message) synchrone journal front-end, écrit dans le journal du processus principal, facilite le débogage
windowControl(name, action) synchrone minimiser/maximiser/fermer/déplacer la fenêtre

Règles d'appel (quatre règles d'or) #

import ZenAPI from './lib/zen_api.js';

// 1. Error checking with isOk() (error is always a number: 0 for success, -1 for a call exception)
const res = await ZenAPI.searchFile('yyztools', 200);
if (!ZenAPI.isOk(res)) { ... }

// 2. Boolean fields returned by interfaces are native booleans, test them directly
//    (exception 1: config values are typed by what the front-end wrote, usually strings, normalize when comparing)
//    (exception 2: isDir in searchFile results is a 1/0 number — hand-assembled JSON path, use truthy or === 1)
const ex = await ZenAPI.exists(path);
if (ex.exists === true) { ... }

// 3. Config writes must be narrow-granularity, full rewrite forbidden
await ZenAPI.setConfig({ sdk_sample: { history } });   // write only your own key

// 4. Batch app info lookup by id uses getAppInfo, looping over searchApp is forbidden
const infos = await ZenAPI.getAppInfo(['calculator', 'ocr']);

Les interfaces asynchrones (getAppInfo / searchFile / le quintette média / ocrRecognition) s'exécutent dans des threads d'arrière-plan ; notez qu'un seul sous-processus média tourne à la fois, et les tâches longues doivent offrir un point d'annulation via cancelRun().

Aide-mémoire des interfaces courantes (capacités au-delà de l'échantillon) #

Scénario Interface
Lire/écrire sa propre configuration getConfig / setConfig (patch à granularité étroite) / addConfig (ajout à une liste)
Ouvrir/enregistrer un fichier browseFile / browseDir / writeFile / readFile (au-delà de 50 Mo utiliser readFileChunk)
Obtenir les répertoires système getKnownDir('download'), etc.
Ouvrir une page/programme externe runAny('https://...', '')
Copier dans le presse-papiers navigator.clipboard côté front (pas besoin de natif pour le texte)
Capture d'écran/OCR screenCap('fast', ...) → ocrRecognition(base64) (toutes deux asynchrones)
Ouvrir la fenêtre d'un autre module windowControl('translate', 'show')

4. Créer le fichier de module .zenmod (fenêtre hôte) #

Créer un .zenmod sous Modules/<catégorie>/ (fichier d'échantillon : sdk/sample/Modules/SDK_Sample.zenmod) :

{
    "id": "sdk_sample",
    "type": "web",
    "name": { "zh_cn": "SDK样例工程", "en": "SDK Sample Project", "...": "共 12 门语言" },
    "desc": { "zh_cn": "基于 MFT 索引的全盘急速文件搜索，支持 Everything 语法", "en": "..." },
    "icon": "fas fa-search",
    "winClassName": "yyzTools::SdkSampleWindowClass",
    "width": 760,
    "height": 540,
    "layoutType": 34,
    "url": "SDK_Sample/index.html",
    "preCreate": 0
}

Description des champs (tous les champs lus par le programme principal pour type:"web") :

Champ Obligatoire Description
id oui globalement unique. Sert aussi de nom de fenêtre pour windowControl/windowState, de appId pour les raccourcis, d'id de montage dock
type oui fixé à web
name oui objet en 12 langues ; écriture en chaîne pure également permise (réservée aux tests internes) ; résolution : langue courante → en → chaîne pure
desc non idem
icon non classe FontAwesome (comme ci-dessus) ou image base64
winClassName non nom de classe de fenêtre Win32, doit juste être globalement unique
width / height non taille initiale de la fenêtre, 800x600 par défaut
layoutType non masque de bits de positionnement initial, 34 = centré horizontalement + centré verticalement
url oui chemin de la page relatif à la racine Web (SDK_Sample/index.html) ; les adresses en ligne commençant par http(s) sont également prises en charge
preCreate non 1 = précréer la fenêtre au démarrage (accélère la première ouverture), 0 par défaut : création à la demande
canSuspend non 1 = autoriser la suspension du WebView quand la fenêtre est cachée pour économiser des ressources (1 par défaut)

Auto-vérification après modification : JSON analysable, UTF-8 sans BOM, id globalement unique, les 12 langues non vides.

L'application est alors terminée — copiez les deux répertoires comme à la section 1 ; cherchez « SDK样例工程 » ou « sdk » dans le panneau de commandes pour la lancer (index pinyin généré automatiquement), ou appelez-la via windowControl('sdk_sample', 'show').

5. Textes multilingues (approche dictionnaire) #

La solution sans build utilise un simple dictionnaire en ES module (i18n.js) :

const messages = {
    zh_cn: { title: 'SDK样例工程', results: '{{count}} 个结果，耗时 {{ms}} ms', ... },
    en:    { title: 'SDK Sample Project', results: '{{count}} results in {{ms}} ms', ... }
};
export function getMessages(lang) { return messages[lang] || messages.en; }
export function interpolate(dict) {
    return (key, params) => { /* {{count}} → params.count */ };
}

À l'initialisation, lire getConfig().language pour choisir la langue, avec repli sur en si introuvable ; les phrases avec espaces réservés sont développées par tf('results', { count, ms }).

Remarques :

  • Les codes de langue utilisent le style underscore minuscule (zh_cn), cohérent avec .zenmod, ce n'est pas du BCP47.

  • Le name/desc du .zenmod doit couvrir les 12 langues ; les textes internes de la page ne sont pas soumis à cette exigence, l'échantillon ne fournit que zh_cn/en, à étendre selon les besoins.

  • Pour les modules devant suivre instantanément la langue de l'interface, le dictionnaire peut devenir un chargement paresseux des fichiers de langue via import() à la demande, le mécanisme étant identique à celui de cet article.

6. Débogage et intégration #

1. Exécution directe sans build (démarrage recommandé) :
   Copier sdk/sample/Web, sdk/sample/Modules dans bin64\ (répertoire de l'exe Release), redémarrer l'exe.
   Après modification du front : windowControl('sdk_sample','close') puis rouvrir, ou redémarrer l'exe.

2. Inspection de la structure dans le navigateur :
   Double-cliquer directement sur Web/SDK_Sample/index.html pour l'ouvrir dans un navigateur.
   Il n'y a pas de window.Zen dans le navigateur ; ZenAPI.call passera par le chemin d'exception avec error: -1,
   la structure / les styles / l'anti-rebond de saisie / la logique de rendu restent débogables (interfaces natives exceptées).

Conseil de performance de recherche : searchFile passe par l'index MFT de tout le disque côté C++, retour généralement en quelques millisecondes ; le côté native dispose d'un mécanisme de slot de recherche — une nouvelle requête évince l'ancienne non terminée (qui retourne un résultat vide) ; côté front, anti-rebond de 300ms + numéro croissant pour écarter les réponses en désordre : des frappes continues ne saturent pas le thread d'arrière-plan ni ne font clignoter d'anciens résultats. L'icône des résultats (base64) est rapportée directement par searchFile, sans appeler getFileIcon en plus.

Si les capacités des interfaces ne suffisent pas (par exemple pour une nouvelle capacité C++), faites part de votre besoin via les canaux de retour du site officiel ; les interfaces seront étendues dans les versions ultérieures du programme principal.

8. Consignes de sécurité #

L'API native expose aux développeurs de modules l'intégralité, sans restriction, des capacités système du processus hôte, y compris des opérations à haut risque telles que la lecture/écriture et la suppression de fichiers, la création et l'arrêt de processus, le contrôle de fenêtres, la lecture/écriture du presse-papiers, la modification des réglages système, l'exécution de commandes, etc., sans boîte de dialogue de permissions, sans isolation en bac à sable (sandbox), sans mécanisme d'annulation.

Évaluez vous-même la sécurité de chaque opération avant de l'appeler : validez toutes les entrées externes, sauvegardez ou demandez confirmation à l'utilisateur avant toute opération irréversible, et n'utilisez que les capacités réellement nécessaires à votre fonction. Toutes les conséquences qui en résultent sont à la charge du développeur.
