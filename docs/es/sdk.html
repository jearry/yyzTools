Referencia de la API Descargar proyecto de ejemplo

Este documento va dirigido a los desarrolladores de módulos y muestra cómo crear desde cero una aplicación web que se ejecuta dentro del proceso principal de yyzTools (tomando como ejemplo el proyecto de muestra del SDK, SDK_Sample—un buscador de archivos ultrarrápido—). Cubre: la estructura de directorios de la página, el alojamiento de la ventana, i18n, la API nativa asíncrona (búsqueda de archivos en todo el disco), la apertura de archivos, la persistencia de la configuración y la plantilla para añadir métodos nativos cuando sea necesario ampliar las capacidades de C++.

La muestra es JS nativo puro, sin dependencias de terceros y sin compilación: no necesita Vite / Alpine / FontAwesome; basta con copiar los directorios Web y Modules al directorio donde se encuentra yyzTools.exe para que funcione.

1. Estructura del ejemplo y forma de despliegue #

sdk/sample/
  Web/                        ← copiar a <directorio de yyzTools.exe>\Web\        (se fusiona con el directorio Web existente)
    SDK_Sample/               ← directorio autocontenido del ejemplo; toda la carpeta es un módulo completo
      index.html              # estructura de la página (DOM nativo, posiciones de texto marcadas con data-i18n)
      filefinder.js           # toda la lógica: búsqueda / apertura / historial / Esc
      filefinder.css          # estilos de la página (todo con variables --zen-*, adaptación automática a modo claro/oscuro)
      i18n.js                 # diccionario de textos (zh_cn / en)
      lib/
        zen_api.js            # clase envolvente ZenAPI (wrapper JS de la API nativa, única dependencia lib)
        window_controls.css   # variables de tema (--zen-*) + estilos de la barra de control de ventana
  Modules/                   ← copiar a <directorio de yyzTools.exe>\Modules\    (se fusiona con el directorio Modules existente)
    SDK_Sample.zenmod         # declaración de módulo type:"web"; ModuleManager crea automáticamente la ventana anfitriona

Despliegue:

Copiar/fusionar sdk/sample/Web     en  bin64\Web\
Copiar/fusionar sdk/sample/Modules en  bin64\Modules\
Reiniciar yyzTools.exe y buscar "SDK样例工程" en el panel de comandos para iniciarlo

Convención sobre dónde lee el programa principal:

Recurso Ubicación
Página <directorio exe>\Web\{page}\index.html
Módulo <directorio exe>\Modules\<categoría>\*.zenmod (solo escanea un nivel de subdirectorios)

2. Vista general de la arquitectura: cómo se ejecuta una aplicación web #

Modules/SDK_Sample.zenmod   ← archivo de módulo que declara type:"web" (basado en datos, sin necesidad de escribir C++)
        │  el programa principal escanea los .zenmod al arrancar
        ▼
Ventana anfitriona WebModule (ventana nativa + WebView2)
        │  carga Web\SDK_Sample\index.html
        ▼
Web/SDK_Sample/             ← todo tu código frontend (JS nativo, sin dependencias)
        │  window.Zen.xxx(...)  ←→  interfaces nativas registradas por el programa principal
        ▼
Managers de C++ (archivos/procesos/ventanas/portapapeles/OCR...)

Conclusiones clave:

  • No es necesario escribir ningún código C++. Un .zenmod con type: "web" es convertido automáticamente por el programa principal en una ventana anfitriona WebModule; el tamaño de la ventana, el icono y el nombre multilingüe se declaran en el propio archivo del módulo.

  • El módulo obtiene automáticamente: búsqueda en el panel de comandos (con índice de pinyin), vinculación de atajos de teclado globales, montaje en el dock y registro en la tabla de nombres de windowControl.

  • El único canal entre el frontend y C++ es window.Zen; llama siempre a través de la clase envolvente ZenAPI (el ejemplo ya incluye lib/zen_api.js).

  • Las páginas sin compilación son directamente archivos estáticos; tras modificarlas basta con actualizar la ventana (windowControl('sdk_sample','hide') y luego show, o reiniciar el exe), sin ningún paso de compilación.

3. Estructura de la página (JS nativo, cuatro archivos) #

index.html #

No incluye ninguna librería de terceros; los tres botones de la barra de control de ventana usan caracteres Unicode como iconos (− / □ / ×), con estilos proporcionados por lib/window_controls.css. Las posiciones de texto se marcan con data-i18n / data-i18n-ph y el JS las rellena de forma uniforme al inicializarse. La estructura se divide en cuatro bloques: barra de búsqueda, chips de historial de búsqueda, barra de estado (número de resultados + ayuda de sintaxis) y lista de resultados:

<div class="search-bar">
    <input type="text" id="searchInput" class="search-input" data-i18n-ph="inputPlaceholder"
           spellcheck="false" autocomplete="off">
    <button class="search-btn" id="btnSearch" data-i18n="search"></button>
</div>
<div class="history-chips" id="historyChips"> ... </div>
<div class="status-bar">
    <span id="statusText" data-i18n="empty"></span>
    <span class="syntax-hint" data-i18n="syntaxHint"></span>
</div>
<div class="result-list" id="resultList"></div>

filefinder.js (lógica principal) #

Cinco responsabilidades, todas copiables directamente del ejemplo:

  1. Control de ventana: ZenAPI.windowControl('sdk_sample', 'min'|'max'|'close'|'drag'); el arrastre de la barra de título solo se activa si el desplazamiento detectado supera los 5 px; tecla Esc: si el cuadro de entrada tiene el foco, primero blur; en caso contrario, cierra la ventana.
  2. Tema: registra window.__applyTheme para recibir los impulsos (push) de C++ (el data-theme de la primera pantalla lo inyecta C++, sin intervención del JS).
  3. i18n: lee getConfig().language, toma los textos del diccionario y recorre los elementos data-i18n rellenándolos; las frases con marcadores {{count}} se expanden con una función de interpolación.
  4. Búsqueda: searchFile(keyword, maxResults) es una interfaz con vinculación asíncrona (se ejecuta en un hilo en segundo plano, sin bloquear la UI); Enter busca de inmediato y la escritura con antirrebote (debounce) de 300 ms busca automáticamente; se usa un número de secuencia creciente para descartar respuestas desordenadas: del lado nativo hay un mecanismo de ranura de búsqueda (una nueva petición desplaza directamente una petición antigua sin terminar, y el Promise antiguo recibe un resultado vacío); el número de secuencia del frontend evita que ese «resultado vacío que llega tarde» sobrescriba el renderizado del nuevo resultado; ambos mecanismos funcionan juntos.
  5. Operaciones sobre resultados: openFile(fullPath, false) abre el archivo (doble clic igual; el segundo parámetro indica «¿con permisos de administrador?»); openFileLocation(fullPath) abre el directorio contenedor; la ruta completa se construye con path + '\\' + name; el icono se toma directamente del campo icon ya presente en el resultado (base64); el tamaño del archivo se formatea a partir del campo numérico size.

Estructura devuelta por searchFile ({ error, files[] }) #

Campos de cada elemento de files[]:

Campo Tipo Descripción
name / path cadena Nombre del archivo / directorio contenedor. Ruta completa = path + '\\' + name
dateModified cadena Fecha de modificación (texto con formato localizado)
size número Tamaño en bytes del archivo, número nativo, listo para usar
icon cadena Icono en base64, utilizable directamente en <img src>, sin necesidad de volver a llamar a getFileIcon
score número Puntuación de relevancia (el lado nativo ya ordena por puntuación)
isDir número 1/0 numérico, no booleano nativo (ruta de JSON ensamblado a mano); evalúa con truthy o === 1, no con === true

Interfaces invocadas por este ejemplo #

Interfaz Vinculación Uso
searchFile(keyword, maxResults) asíncrona Búsqueda sobre el índice MFT de todo el disco, con sintaxis estilo Everything (size:>100MB, ext:mp4, !ext:tmp)
openFile(path, admin) síncrona Abre archivo/directorio (comportamiento predeterminado del shell), con permisos de administrador si admin=true
openFileLocation(path) síncrona Localiza el archivo en el Explorador de archivos
getConfig(key?) síncrona Lee la configuración: sin parámetro devuelve todo; con key toma solo esa clave (admite rutas con puntos a.b)
setConfig(patch, replace?) síncrona Escritura de granularidad fina del historial de búsqueda: setConfig({ sdk_sample: { history } }); replace=true reemplaza todo (solo para importar copias de seguridad)
log(message) síncrona Registro del frontend; se escribe en el log del proceso principal para facilitar el diagnóstico
windowControl(name, action) síncrona Minimizar/maximizar/cerrar/arrastrar la ventana

Normas de invocación (cuatro reglas de oro) #

import ZenAPI from './lib/zen_api.js';

// 1. Usa isOk() para detectar errores (error es siempre un número: 0 éxito, -1 indica una excepción en la llamada)
const res = await ZenAPI.searchFile('yyztools', 200);
if (!ZenAPI.isOk(res)) { ... }

// 2. Los campos booleanos devueltos por las interfaces son booleanos nativos; evalúalos directamente
//    (excepción uno: el tipo de los valores de config depende de lo que escribió el frontend, suelen ser cadenas; normaliza al comparar)
//    (excepción dos: el isDir de los resultados de searchFile es un número 1/0—ruta de JSON ensamblado a mano; usa truthy o === 1)
const ex = await ZenAPI.exists(path);
if (ex.exists === true) { ... }

// 3. La escritura de configuración debe ser de granularidad fina; prohibido reescribir todo
await ZenAPI.setConfig({ sdk_sample: { history } });   // escribe solo tu propia clave

// 4. Para obtener información de aplicaciones en lote por id usa getAppInfo; prohibido iterar con searchApp
const infos = await ZenAPI.getAppInfo(['calculator', 'ocr']);

Las interfaces asíncronas (getAppInfo / searchFile / el quinteto de medios / ocrRecognition) se ejecutan en un hilo en segundo plano; ten en cuenta que en un mismo momento solo hay un subproceso de medios en ejecución, y las tareas largas deben ofrecer un punto de cancelación con cancelRun().

Referencia rápida de interfaces comunes (más capacidades fuera del ejemplo) #

Escenario Interfaz
Leer/escribir tu propia configuración getConfig / setConfig (patch de granularidad fina) / addConfig (añadir elementos a una lista)
Abrir/guardar archivos browseFile / browseDir / writeFile / readFile (>50 MB usa readFileChunk)
Obtener directorios del sistema getKnownDir('download'), etc.
Abrir webs/programas externos runAny('https://...', '')
Copiar al portapapeles navigator.clipboard del frontend (no se necesita native para texto)
Captura de pantalla/OCR screenCap('fast', ...) → ocrRecognition(base64) (ambas asíncronas)
Abrir la ventana de otro módulo windowControl('translate', 'show')

4. Crear el archivo de módulo .zenmod (anfitrión de la ventana) #

Crea un nuevo .zenmod en Modules/<categoría>/ (archivo del ejemplo: sdk/sample/Modules/SDK_Sample.zenmod):

{
    "id": "sdk_sample",
    "type": "web",
    "name": { "zh_cn": "SDK样例工程", "en": "SDK Sample Project", "...": "12 idiomas en total" },
    "desc": { "zh_cn": "基于 MFT 索引的全盘急速文件搜索，支持 Everything 语法", "en": "..." },
    "icon": "fas fa-search",
    "winClassName": "yyzTools::SdkSampleWindowClass",
    "width": 760,
    "height": 540,
    "layoutType": 34,
    "url": "SDK_Sample/index.html",
    "preCreate": 0
}

Descripción de los campos (todos los campos que lee el programa principal cuando type:"web"):

Campo Obligatorio Descripción
id Sí Único a nivel global. Es a la vez el nombre de ventana para windowControl/windowState, el appId de los atajos y el id de montaje en el dock
type Sí Fijo web
name Sí Objeto con los 12 idiomas; también se admite una cadena simple (solo recomendado para pruebas internas); orden de resolución: idioma actual → en → cadena simple
desc No Igual que el anterior
icon No Clase de FontAwesome (como arriba) o imagen en base64
winClassName No Nombre de la clase de ventana Win32; basta con que sea único a nivel global
width / height No Tamaño inicial de la ventana, por defecto 800x600
layoutType No Máscara de bits de la posición inicial; 34 = centrado horizontal + centrado vertical
url Sí Ruta de la página relativa a la raíz de Web (SDK_Sample/index.html); también admite direcciones en línea que empiecen por http(s)
preCreate No 1 = precrear la ventana al arrancar (acelera la primera apertura); por defecto 0, se crea bajo demanda
canSuspend No 1 = permite suspender el WebView cuando la ventana esté oculta para ahorrar recursos (por defecto 1)

Autoverificación tras la edición: JSON analizable, UTF-8 sin BOM, id único a nivel global y los 12 idiomas no vacíos.

Con esto la aplicación ya está terminada: copia los dos directorios como se indica en la sección 1, busca "SDK样例工程" o "sdk" en el panel de comandos para iniciarla (el índice de pinyin se genera automáticamente); también puedes invocarla con windowControl('sdk_sample', 'show').

5. Textos multilingües (mediante diccionario) #

La solución sin compilación usa un diccionario como módulo ES normal (i18n.js):

const messages = {
    zh_cn: { title: 'SDK样例工程', results: '{{count}} 个结果，耗时 {{ms}} ms', ... },
    en:    { title: 'SDK Sample Project', results: '{{count}} results in {{ms}} ms', ... }
};
export function getMessages(lang) { return messages[lang] || messages.en; }
export function interpolate(dict) {
    return (key, params) => { /* {{count}} → params.count */ };
}

Al inicializar, lee getConfig().language para elegir el idioma; si no se encuentra, recurre a en; las frases con marcadores se expanden con tf('results', { count, ms }).

Notas:

  • Los códigos de idioma usan el estilo minúsculas con guion bajo (zh_cn), igual que .zenmod; no es BCP47.

  • El name/desc del .zenmod debe estar completo en los 12 idiomas; los textos dentro de la página no tienen este requisito obligatorio; el ejemplo solo incluye zh_cn/en, amplíalo según necesites.

  • Los módulos que deban cambiar de idioma de forma inmediata junto con la interfaz pueden convertir el diccionario en archivos multilingües con carga diferida mediante import() bajo demanda; el mecanismo es el mismo que el de este documento.

6. Depuración e integración #

1. Ejecutar directamente sin compilar (recomendado para empezar):
   Copia sdk/sample/Web y sdk/sample/Modules a bin64\ (directorio del exe Release) y reinicia el exe.
   Tras modificar el frontend, haz windowControl('sdk_sample','close') y vuelve a abrir, o reinicia el exe.

2. Ver la estructura en el navegador:
   Abre directamente Web/SDK_Sample/index.html con doble clic.
   En el navegador no existe window.Zen, por lo que ZenAPI.call tomará la ruta de excepción y devolverá error: -1;
   la estructura de la página / estilos / antirrebote de entrada / lógica de renderizado se pueden depurar con normalidad (excepto las interfaces nativas).

Consejo de rendimiento de búsqueda: searchFile usa el índice MFT de todo el disco en el lado C++ y normalmente devuelve en milisegundos; el lado nativo tiene un mecanismo de ranura de búsqueda—una nueva petición desplaza la antigua sin terminar (que devuelve un resultado vacío)—y el frontend combina un antirrebote de 300 ms + un número de secuencia creciente para descartar respuestas desordenadas, de modo que una escritura continua tampoco satura el hilo en segundo plano ni hace parpadear resultados antiguos. Los iconos de los resultados (base64) los devuelve searchFile de paso, sin necesidad de llamar aparte a getFileIcon.

Si las capacidades de las interfaces no bastan (por ejemplo, si necesitas nuevas funciones de C++), puedes plantear la petición por los canales de comentarios del sitio web oficial, y el programa principal ampliará las interfaces en versiones posteriores.

8. Advertencias de seguridad #

La API nativa expone a los desarrolladores de módulos de forma completamente abierta las capacidades del sistema del proceso anfitrión, entre ellas operaciones de alto riesgo como la lectura, escritura y eliminación de archivos, la creación y terminación de procesos, el control de ventanas, la lectura y escritura del portapapeles, la modificación de la configuración del sistema y la ejecución de líneas de comandos, sin diálogos de permisos, sin aislamiento de sandbox y sin mecanismo de deshacer.

Antes de cada llamada evalúa por ti mismo la seguridad de cada operación: valida todas las entradas externas, haz una copia de seguridad o pide confirmación al usuario antes de operaciones irreversibles, y usa únicamente las capacidades que la función realmente necesite. El desarrollador asume toda responsabilidad por las consecuencias que de ello se deriven.
