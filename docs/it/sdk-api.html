1. Convenzioni generali #

Questo documento definisce tutte le interfacce relative all'interazione con il livello nativo e copre solo le interfacce registrate dal processo principale yyzTools.exe (SetupBindings() in src/yyztools/NativeApi.cpp).

Modalità di chiamata #

  • Il front-end richiama le funzioni dell'interfaccia tramite l'oggetto window.Zen; si raccomanda di passare in modo uniforme dalla classe wrapper ZenAPI: web/lib/zen_api.js, senza collegarsi direttamente a window.Zen nel codice di business, così da poterla usare come livello di compatibilità delle interfacce in caso di aggiustamenti in futuro.

  • Input: passati con parametri posizionali; per numero e tipo dei parametri consultare la singola interfaccia

  • Output: restituito tramite valore di ritorno, un oggetto json con il seguente contenuto

    {
    "error": 0,
    "errorMsg": "",
    ...
}

    • error: 0 corretto, diverso da 0 errore

    • errorMsg (opzionale): messaggio d'errore

    • Altri (opzionale): consultare la singola interfaccia

Controllo degli errori #

error è sempre un numero: 0 corretto, diverso da 0 errore (-1 in caso di eccezione di chiamata).

Binding sincrono / asincrono #

La stragrande maggioranza delle interfacce usa il binding sincrono (BindSync), che restituisce subito. Le seguenti 7 interfacce usano il binding asincrono (BindAsync), eseguito su un thread in background con risoluzione tramite Promise, senza bloccare il thread UI:

getAppInfo, searchFile, imageRun, ffmpegRun, pdfRun, gsRun, ocrRecognition

Per i vincoli comportamentali delle interfacce asincrone in un dato istante consultare le singole voci (ad esempio la cinquina media viene eseguita in serie e condivide cancelRun per l'annullamento).

2. Ottenere la configurazione #

function Zen.getConfig(key?: string) : object

  • Input

    • key (opzionale): legge solo quella chiave, supporta percorsi con punto a.b. Senza parametri restituisce l'intera configurazione.

      • Corrispondenza trovata: restituisce {"error":0, "<key>": <valore>}, ad esempio getConfig("language") → {"error":0,"language":"zh_cn"}; getConfig("dock.categories") → {"error":0,"dock":{"categories":[...]}}

      • Nessuna corrispondenza: restituisce {"error":0} (non segnala errore, spetta al chiamante gestire il fallback)

  • Output (esempio; i campi reali dipendono dalla configurazione effettiva)

    {
    "error": 0,
    "errorMsg": "",
    "logLevel": "1",
    "wallpaperEnabled": "1",
    "overlayEnabled": "0",
    "gameMode": "0",
    "clipboardHistoryMaxCount": "500",
    "autoStart": "1",
    "shortcutKeys": {
        "main": {
            "doubleCtrlEnabled": "1",
            "doubleAltEnabled": "1",
            "modifier": 1,
            "virtualCode": 32
        },
        "apps": [
            {
                "appId": "translate",
                "modifier": 1,
                "virtualCode": 49
            },
            {
                "appId": "ocr",
                "modifier": 1,
                "virtualCode": 50
            }
        ]
    },
    "quickOpen": [
        {
            "name": "谷歌搜索",
            "type": "normal",
            "index": "0",
            "url": "https://www.google.com/search?q={query}",
            "enabled": "1"
        }
    ],
    "customApps": [
        {
            "filePath": "d:\test\test1.exe",
            "enabled": "1"
        }
    ]
}

    • logLevel: livello di log (0: Trace / 1: Debug / 2: Info / 3: Warning / 4: Error / 5: Fatal)

    • wallpaperEnabled: abilitazione dello sfondo desktop dinamico

    • overlayEnabled: abilitazione degli effetti del desktop

    • gameMode: modalità gioco

    • clipboardHistoryMaxCount: numero massimo di voci nella cronologia degli appunti

    • autoStart: avvio automatico all'accensione

    • shortcutKeys: tasti di scelta rapidi globali

      • main: interfaccia principale

        • doubleCtrlEnabled: attivazione con doppio Ctrl

        • doubleAltEnabled: attivazione con doppio Alt

        • modifier: tasto modificatore

        • virtualCode: tasto principale

      • apps: applicazioni

        • appId: id dell'applicazione

        • modifier: tasto modificatore

        • virtualCode: tasto principale

    • quickOpen: apertura rapida

      • name: nome

      • type: tipo (normal: ricerca generale / spec: ricerca verticale)

      • index: indice

      • url: template url

      • enabled: abilitato o meno

    • customApps: app personalizzate

      • filePath: percorso dell'exe corrispondente all'app

      • enabled: abilitato o meno

    • dock: dock (categorie + contenuti)

      • Convenzione generale: l'assenza di name/icon indica "usa i valori predefiniti interni" (derivati a runtime da i18n o dal .zenmod corrispondente all' appId; cambiano con la lingua dell'interfaccia); la presenza del campo indica che l'utente l'ha personalizzato e va mostrato così com'è, senza tradurlo.**

      • categories: categorie

        • id: le categorie integrate sono id semantici (folder/tools/ai/game/system), quelle create dall'utente sono category_<timestamp>

        • name: opzionale, presente solo dopo una rinomina da parte dell'utente

        • icon: classe FontAwesome

        • color: colore del tema

        • order: indice di ordinamento

      • contents: voci di contenuto

        • id: le voci di directory integrate sono id semantici (desktop/documents/downloads/music/videos), le altre sono content_<timestamp>

        • categoryId: id della categoria di appartenenza

        • type: app | folder | url

        • appId: obbligatorio quando type=app, corrisponde all'id del .zenmod; nome e icona sono tutti derivati da esso, non salvarli su disco

        • folderPath: obbligatorio quando type=folder, supporta variabili d'ambiente come %USERPROFILE%

        • url: obbligatorio quando type=url, URL completo normalizzato (senza prefisso di protocollo viene aggiunto automaticamente https://); al clic si apre con il browser predefinito del sistema. Il nome è inserito dall'utente, l'icona viene recuperata a runtime dal favicon del sito (fallback fas fa-globe in caso di fallimento), non salvarla su disco

        • name / icon: opzionali, stesso significato di sopra (obbligatori per le directory scelte dall'utente con type=folder)

        • color: tinta dell'icona

        • order: indice di ordinamento all'interno della stessa categoria

3. Modificare la configurazione #

function Zen.setConfig(config: json_obj, replace?: boolean) : object

  • Input

    • config: come getConfig

      • passare solo ciò che si vuole modificare, senza dover passare tutto il contenuto

      • il contenuto sotto la stessa coppia chiave/valore va passato per intero

      {
    "logLevel": "1"
}

    • replace (opzionale, predefinito false): false=unione incrementale alla configurazione esistente, true=sostituzione totale (per l'import di backup, consente di rimuovere le voci di elenco eliminate). Passare la stringa "true" o "false"; in assenza equivale a "false".

  • Attenzione: non "leggere tutto con getConfig e riscrivere tutto con setConfig" — il valore di ritorno di getConfig contiene il campo error, e riscriverlo per intero lo salverebbe nel file di configurazione. Scrivere sempre a granularità ristretta, ad esempio setConfig({ dock: { categories } }).

  • Output

    {
    "error": 0,
    "errorMsg": ""
}

3. Ottenere lo stato della finestra #

function Zen.windowState(window: string, can_suspend?: boolean) : object

  • Input

    • window: Name o forma stringa dell'HWND, vedere controllo delle finestre

    • can_suspend (opzionale): consentire o meno la sospensione della WebView di quella finestra (interruttore di risparmio risorse, predefinito false)

  • Output

    "error": 0,
    "errorMsg": "",
    "state": "show",
    "topmost": "0"
}

    • state: stato (show: visualizzazione normale / min: ridotta a icona / max: massimizzata / close: chiusa)

    • topmost: in primo piano o meno

2. Ottenere le informazioni delle app in batch per id (asincrono) #

function Zen.getAppInfo(appIds: string[]) : object

Nella configurazione viene salvato solo appId; nome e icona sono sempre derivati a runtime (il name del .zenmod è multilingue, una snapshot salvata nella configurazione risulterebbe obsoleta dopo un cambio lingua). Questa interfaccia esiste proprio per questo scenario.

⚠️ Non sostituirla con un ciclo di searchApp(appId, 1): searchApp esegue ogni volta una scansione completa dell'intero indice delle applicazioni + matching pinyin + punteggio e ordinamento, avvia inoltre due thread in parallelo e restituisce più risultati con icone base64. Dock più tasti di scelta rapidi fanno decine di appId: interrogarli uno per uno rallenterebbe sensibilmente l'avvio. Questa interfaccia riceve tutto in una volta e sul lato nativo usa map::find con corrispondenza esatta.

Attende internamente che l'indice delle applicazioni sia pronto (l'indice è generato da un thread in background), per questo è un binding asincrono: chiamarla nel precochio di un avvio a freddo non restituisce risultati vuoti.

  • Input

    • appIds: array di appId, ad esempio ["calculator", "Microsoft.WindowsCamera"]

  • Output

    Formato identico a searchApp (stesso BuildAppResult), ma:

    • restituisce solo le voci con corrispondenza esatta, gli id non trovati vengono silenziosamente saltati, quindi apps.length può essere minore della lunghezza dell'input (utile per rilevare appId non più validi nella configurazione)

    • l'ordine segue quello dell'input, score è sempre 0 (non partecipa al punteggio)

    {
    "error": 0,
    "apps": [
        {
            "id": "calculator",
            "name": "超级计算器",
            "path": "calculator",
            "desc": "",
            "icon": "data:image/png;base64,",
            "appType": 4,
            "score": 0
        }
    ]
}

6. Operazioni sui file #

1. Cercare file (asincrono) #

function Zen.searchFile(keyword: string, maxResults : number) : object

  • Nota: la ricerca è eseguita dal servizio proprietario yyzFileSearch (indice MFT + IPC tramite named pipe), supporta una sintassi di query in stile Everything (ad esempio size:>100MB, !ext:mp4) e i risultati sono ordinati per pertinenza. La ricerca è eseguita su un thread in background, con binding asincrono.

7. Elaborazione media #

La cinquina media è eseguita dal lato C++ richiamando gli strumenti CLI di terze parti in bin64\Platform\. Tranne ffprobeRun, tutte usano il binding asincrono (esecuzione su thread in background, senza bloccare il thread UI); l'elaborazione in batch è seriale e in un dato istante è in esecuzione un solo sottoprocesso; è possibile terminare l'esecuzione corrente con Zen.cancelRun() (in caso di annullamento restituisce errorMsg: "cancelled").

  "error": 0,

9. Crittografia e decrittografia #

1. Crittografare dati #

function Zen.encrypt(target: string, algorithm: string, type: string, key: string, iv: string) : object

  • Input

    • target: dati da crittografare

      • con type="text" è una stringa di testo

      • con type="data" sono dati binari in codifica Base64

      • con type="hex" è una stringa esadecimale

      • con type="file" è un percorso di file

    • algorithm: algoritmo di crittografia

      • crittografia simmetrica: "aes-128-cbc", "aes-192-cbc", "aes-256-cbc", "aes-128-ecb", "aes-256-ecb", "aes-128-ctr", "aes-256-ctr", "des-cbc", "des-ecb", "des-ede3-cbc" (3DES), "des-ede3-ecb", "rc4", "bf-ecb" (Blowfish), "rc2-cbc", "sm4-cbc", "sm4-ecb", "sm4-ctr"

      • crittografia asimmetrica: "rsa-pkcs1", "rsa-oaep" (RSA, cifratura con chiave pubblica e decifratura con chiave privata), "sm2" (curva ellittica nazionale sm2p256v1, cifratura con chiave pubblica e decifratura con chiave privata; in un'unica operazione può processare lunghezze arbitrarie, senza necessità di suddivisione in blocchi)

      • key/iv sono in Base64; convertiti internamente in esadecimale e passati nella forma enc -K <hex> -iv <hex>, la lunghezza della chiave deve corrispondere esattamente all'algoritmo

    • type: tipo di input (predefinito "text")

      • "text": dati testuali

      • "data": dati binari in codifica Base64

      • "hex": stringa esadecimale

      • "file": percorso di file

    • key: per la crittografia simmetrica chiave in codifica Base64; per l'asimmetrico (rsa-*, sm2) testo PEM (per la cifratura si passa la chiave pubblica, per la decifratura quella privata, passata tale e quale senza decodifica Base64)

    • iv: vettore di inizializzazione in codifica Base64 (opzionale, richiesto da alcuni algoritmi; ignorato nell'asimmetrico)

  • Output

    {
  "error": 0,
  "result": "Base64编码的加密数据",
  "algorithm": "aes-256-cbc",
  "type": "text",
  "inputSize": 1024,
  "outputSize": 1040
}

5. Calcolare un hash #

function Zen.calcHash(target: string, algorithm: string, type?: string, key?: string) : object

  • Input

    • target: oggetto del calcolo, il significato varia con type

      • con type="file" è un percorso di file

      • con type="text" è una stringa di testo (il digest è calcolato in UTF-8)

      • con type="data" sono dati binari in codifica Base64

      • con type="hex" è una stringa esadecimale

    • algorithm: algoritmo di hash

      • "md5"

      • "sha1"

      • "sha224"

      • "sha256"

      • "sha384"

      • "sha512"

      • "ripemd160"

      • "sm3" (digest nazionale SM3, 256 bit / 64 cifre esadecimali)

      • "sha3-224" / "sha3-256" / "sha3-384" / "sha3-512" (SHA-3 / Keccak, NIST FIPS 202)

      • "blake2b512" / "blake2s256" (BLAKE2, digest moderni ad alte prestazioni)

      • "crc32" (checksum CRC32, 8 cifre esadecimali)

      • "crc16" (checksum CRC16, 4 cifre esadecimali)

      • "checksum" (somma cumulata dei byte, 8 cifre esadecimali)

      • "hmac-md5" / "hmac-sha1" / "hmac-sha256" / "hmac-sha512" / "hmac-sm3" / "hmac-sha3-256" / "hmac-sha3-512" (HMAC, il quarto parametro key è la chiave, l'output è un MAC esadecimale)

    • type: tipo di input (opzionale, predefinito "file")

      • "file": calcola l'hash di un file

      • "text": calcola l'hash di un testo

      • "data": calcola l'hash di dati binari (target deve essere una stringa Base64)

      • "hex": calcola l'hash di una stringa esadecimale (target è una stringa hex, calcolata per byte dopo la decodifica)

  • Output

    {
  "error": 0,
  "hash": "D41D8CD98F00B204E9800998ECF8427E",
  "algorithm": "md5",
  "type": "file"
}

13. Aggiornamento #

L'aggiornamento è completato dal processo indipendente yyzUpdater.exe; il processo principale si occupa solo di avviarlo e sondarne lo stato.

1. Verificare gli aggiornamenti #

function Zen.checkUpdate() : object

Avvia yyzUpdater.exe --check-and-apply (verifica + download + applicazione in un'unica soluzione).

  • Input: nessuno

  • Output

    { "error": 0, "errorMsg": "success" }

    Nota: error:0 indica solo che l'updater è stato avviato con successo, non rappresenta il risultato dell'aggiornamento. Lo stato dell'aggiornamento in corso/pronto si interroga con getUpdateState.

2. Ottenere lo stato dell'aggiornamento #

function Zen.getUpdateState() : object

Sonda in tempo reale lo stato dell'aggiornamento (per il polling della tray):

  • se l'updater è in esecuzione → mutex singleton Local\yyzUpdater_SingleInstance

  • se l'aggiornamento è già stato scaricato e in attesa di applicazione → esistenza di %APPDATA%\yyzTools\Update\update.ready (se esiste, ne viene analizzata la version del pacchetto main)

  • se la verifica manuale è terminata senza aggiornamenti → marker %APPDATA%\yyzTools\Update\update.result (lettura ed eliminazione immediata)

  • Input: nessuno

  • Output

    { "error": 0, "status": "idle", "version": "", "lastResult": "" }

    • status: idle (nessuna attività di aggiornamento) / checking (updater in esecuzione) / ready (già scaricato, pronto per l'aggiornamento)

    • version: ha valore solo nello stato ready, con il numero della nuova versione da applicare (presa dal pacchetto main); negli altri casi stringa vuota

    • lastResult: può avere valore solo nello stato idle, con il risultato dell'ultima verifica manuale (--check-and-apply): uptodate (già aggiornato) / error (verifica fallita); senza marker è una stringa vuota. Il marker è scritto dall'updater e subito eliminato dopo la lettura da questa interfaccia, quindi viene restituito una sola volta, per mostrare un Toast nel front-end; la verifica silenziosa --check non scrive il marker e non genera disturbi.

    • Priorità degli stati: checking > ready > idle

3. Applicare l'aggiornamento già scaricato #

function Zen.applyUpdate() : object

Avvia yyzUpdater.exe --apply: legge update.ready → attende l'uscita del processo principale → sostituisce i file → riavvia il processo principale. Da chiamare solo quando getUpdateState restituisce ready.

  • Input: nessuno

  • Output

    { "error": 0, "errorMsg": "success" }

⚠️ Note sulla sicurezza #

Le Native API offrono agli sviluppatori di moduli accesso completo alle capacità di sistema del processo host, incluse operazioni ad alto rischio come lettura/scrittura ed eliminazione di file, creazione e terminazione di processi, controllo delle finestre, lettura/scrittura degli appunti, modifica del registro e delle impostazioni di sistema, download dalla rete ed esecuzione di comandi da riga di comando.

Queste interfacce non prevedono finestre di dialogo per i permessi, non applicano isolamento sandbox, non offrono meccanismi di annullamento — la chiamata ha effetto immediato con i permessi dell'utente corrente, e un uso improprio può causare la perdita permanente di dati o malfunzionamenti del sistema.

Pertanto si prega di prestare attenzione a:

  • Valutare autonomamente la sicurezza: prima di chiamare qualsiasi interfaccia, verificare che i parametri (in particolare percorsi, nomi di processi, righe di comando) provengano da fonti affidabili e siano stati adeguatamente validati; per operazioni irreversibili come eliminazioni, sovrascritture o terminazione di processi, si consiglia di fare prima un backup o chiedere una seconda conferma all'utente.
  • Diffidare degli input non affidabili: non concatenare mai direttamente input dell'utente, risposte di rete o dati di terze parti nei parametri delle interfacce senza validarli, per prevenire path traversal e injection di comandi.
  • Principio dei privilegi minimi: richiedere solo le capacità realmente necessarie alla propria funzione, evitando per comodità interfacce con un impatto più ampio.
  • Responsabilità propria: lo sviluppatore deve assumersi ogni conseguenza derivante dall'uso di questa API, incluse a titolo esemplificativo perdita di dati, danni al sistema e rischi per la sicurezza.
