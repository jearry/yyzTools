Guida introduttiva

Crea il tuo primo modulo senza strumenti di build

Riferimento API Scarica il progetto di esempio

Questo documento è rivolto agli sviluppatori di moduli e mostra come creare da zero un'app Web in esecuzione all'interno del processo principale di yyzTools (prendendo come esempio il progetto campione dell'SDK SDK_Sample — un velocissimo motore di ricerca file). Copre: la struttura delle directory della pagina, la finestra host, l'i18n, le Native API asincrone (ricerca file su tutto il disco), l'apertura dei file, la persistenza della configurazione e il modello per aggiungere nuovi metodi nativi quando serve estendere le capacità C++.

L'esempio è JS nativo puro, zero dipendenze di terze parti, senza build: non servono Vite / Alpine / FontAwesome; basta copiare le due directory Web e Modules nella directory di yyzTools.exe per eseguirlo.

1. Struttura della directory campione e modalità di distribuzione #

sdk/sample/
  Web/                        ← copiare in <directory di yyzTools.exe>\Web\        (fusione con la directory Web esistente)
    SDK_Sample/               ← directory autonoma dell'esempio, l'intera cartella è un modulo completo
      index.html              # struttura della pagina (DOM nativo, posizioni dei testi marcate con data-i18n)
      filefinder.js           # tutta la logica: ricerca / apertura / cronologia / Esc
      filefinder.css          # stili della pagina (esclusivamente variabili --zen-*, adattamento automatico a tema chiaro/scuro)
      i18n.js                 # dizionario dei testi (zh_cn / en)
      lib/
        zen_api.js            # classe wrapper ZenAPI (wrapper JS delle Native API, unica dipendenza di lib)
        window_controls.css   # variabili del tema (--zen-*) + stili della barra di controllo finestra
  Modules/                   ← copiare in <directory di yyzTools.exe>\Modules\    (fusione con la directory Modules esistente)
    SDK_Sample.zenmod         # dichiarazione del modulo type:"web", ModuleManager crea automaticamente la finestra host

Distribuzione:

Copiare/fondere sdk/sample/Web     in  bin64\Web\
Copiare/fondere sdk/sample/Modules in  bin64\Modules\
Riavviare yyzTools.exe, cercare "SDK样例工程" nel pannello comandi per avviarlo

Convenzioni sui percorsi letti dal programma principale:

Risorsa Posizione
Pagina <dir exe>\Web\{page}\index.html
Modulo <dir exe>\Modules\<categoria>\*.zenmod (scansione limitata a un livello di sottodirectory)

2. Panoramica dell'architettura: come viene eseguita un'app Web #

Modules/SDK_Sample.zenmod   ← file di dichiarazione del modulo type:"web" (data-driven, senza scrivere C++)
        │  il programma principale esegue la scansione dei .zenmod all'avvio
        ▼
Finestra host WebModule (finestra nativa + WebView2)
        │  carica Web\SDK_Sample\index.html
        ▼
Web/SDK_Sample/             ← tutto il codice front-end (JS nativo, zero dipendenze)
        │  window.Zen.xxx(...)  ←→  interfacce native registrate dal programma principale
        ▼
Manager C++ (file/processi/finestre/appunti/OCR...)

Conclusioni chiave:

  • Non è necessario scrivere alcun codice C++. Un .zenmod con type: "web" viene trasformato automaticamente dal programma principale in una finestra host WebModule; dimensione della finestra, icona e nome multilingua sono tutti dichiarati nel file del modulo.

  • Il modulo ottiene automaticamente: la ricerca nel pannello comandi (con indice pinyin), il binding dei tasti di scelta rapidi globali, il montaggio nel dock e la registrazione nella tabella dei nomi di windowControl.

  • L'unico canale tra front-end e C++ è window.Zen; si raccomanda di chiamarlo sempre tramite la classe wrapper ZenAPI (l'esempio include già lib/zen_api.js).

  • Le pagine senza build sono direttamente file statici: dopo le modifiche basta aggiornare la finestra (con windowControl('sdk_sample','hide') seguito da show, oppure riavviando l'exe), senza alcun passaggio di compilazione.

3. Struttura della pagina (JS nativo, quattro file) #

index.html #

Non include alcuna libreria di terze parti; i tre pulsanti della barra di controllo finestra usano caratteri Unicode come icone (− / □ / ×) e lo stile è fornito da lib/window_controls.css. Le posizioni dei testi sono marcate con data-i18n / data-i18n-ph e riempite in modo uniforme all'inizializzazione del JS. La struttura si divide in quattro blocchi: barra di ricerca, chip della cronologia di ricerca, barra di stato (numero di risultati + suggerimento sintassi), elenco dei risultati:

<div class="search-bar">
    <input type="text" id="searchInput" class="search-input" data-i18n-ph="inputPlaceholder"
           spellcheck="false" autocomplete="off">
    <button class="search-btn" id="btnSearch" data-i18n="search"></button>
</div>
<div class="history-chips" id="historyChips"> ... </div>
<div class="status-bar">
    <span id="statusText" data-i18n="empty"></span>
    <span class="syntax-hint" data-i18n="syntaxHint"></span>
</div>
<div class="result-list" id="resultList"></div>

filefinder.js (logica principale) #

Cinque responsabilità, basta copiarle così come sono dall'esempio:

  1. Controllo finestra: ZenAPI.windowControl('sdk_sample', 'min'|'max'|'close'|'drag'); il trascinamento della barra del titolo si attiva solo quando lo spostamento supera 5px; tasto Esc — se l'input ha il focus prima viene tolto il focus (blur), altrimenti si chiude la finestra.
  2. Tema: registrare window.__applyTheme per ricevere le notifiche push dal C++ (il data-theme della prima schermata è iniettato dal C++, nessuna gestione JS necessaria).
  3. i18n: leggere getConfig().language, prendere i testi dal dizionario e riempire gli elementi data-i18n; le frasi con segnaposto {{count}} vengono espanse con una funzione di interpolazione.
  4. Ricerca: searchFile(keyword, maxResults) è un'interfaccia con binding asincrono (eseguita su un thread in background, non blocca la UI); Invio ricerca immediata, input con debounce di 300ms per la ricerca automatica; si usa un numero progressivo per scartare le risposte fuori ordine — il lato nativo ha un meccanismo a slot di ricerca (una nuova richiesta rimpiazzta direttamente la vecchia non ancora completata, e il vecchio Promise riceve un risultato vuoto); il numero progressivo del front-end impedisce che questo "risultato vuoto in ritardo" sovrascriva il rendering del nuovo risultato: i due meccanismi cooperano.
  5. Operazioni sui risultati: openFile(fullPath, false) apre il file (idem con doppio clic; il secondo parametro indica "con privilegi di amministratore"); openFileLocation(fullPath) apre la directory che lo contiene; il percorso completo è composto da path + '\\' + name; l'icona usa direttamente il campo icon già presente nel risultato (base64); la dimensione del file viene formattata dal campo numerico size.

Struttura di ritorno di searchFile ({ error, files[] }) #

Campi di ogni elemento di files[]:

Campo Tipo Descrizione
name / path stringa Nome del file / directory che lo contiene. Percorso completo = path + '\\' + name
dateModified stringa Data di modifica (testo in formato localizzato)
size numero Dimensione del file in byte, numero nativo, usabile direttamente
icon stringa Icona base64, utilizzabile direttamente in <img src>, senza bisogno di richiamare getFileIcon
score numero Punteggio di pertinenza (il nativo ordina già per punteggio)
isDir numero 1/0 numerico e non booleano nativo (percorso JSON costruito a mano), verificare con truthy o === 1, non === true

Riepilogo delle interfacce richiamate in questo esempio #

Interfaccia Binding Uso
searchFile(keyword, maxResults) asincrono Ricerca sull'indice MFT di tutto il disco, supporta la sintassi Everything (size:>100MB, ext:mp4, !ext:tmp)
openFile(path, admin) sincrono Apre file/directory (comportamento predefinito della shell), con admin=true con privilegi di amministratore
openFileLocation(path) sincrono Individua il file in Esplora risorse
getConfig(key?) sincrono Legge la configurazione: senza parametri restituisce tutto, con una key solo quella chiave (supporta percorsi con punto a.b)
setConfig(patch, replace?) sincrono Scrittura a granularità ristretta della cronologia di ricerca: setConfig({ sdk_sample: { history } }); replace=true sostituzione totale (solo per import di backup)
log(message) sincrono Log del front-end, scritto nel log del processo principale, utile per il debug
windowControl(name, action) sincrono Riduzione a icona / massimizzazione / chiusura / trascinamento della finestra

Regole di chiamata (quattro regole ferree) #

import ZenAPI from './lib/zen_api.js';

// 1. Per il controllo errori usare isOk() (error è sempre un numero: 0 successo, -1 indica un'eccezione di chiamata)
const res = await ZenAPI.searchFile('yyztools', 200);
if (!ZenAPI.isOk(res)) { ... }

// 2. I campi booleani restituiti dalle interfacce sono booleani nativi, verificabili direttamente
//    (eccezione uno: i valori di config hanno il tipo deciso dalla scrittura del front-end, in genere stringhe, fare attenzione alla normalizzazione nei confronti)
//    (eccezione due: isDir del risultato di searchFile è 1/0 numerico — percorso JSON costruito a mano, usare truthy o === 1)
const ex = await ZenAPI.exists(path);
if (ex.exists === true) { ... }

// 3. La scrittura della configurazione deve essere a granularità ristretta, vietata la riscrittura integrale
await ZenAPI.setConfig({ sdk_sample: { history } });   // scrive solo la propria chiave

// 4. Per le info app in batch per id usare getAppInfo, vietato ciclare su searchApp
const infos = await ZenAPI.getAppInfo(['calculator', 'ocr']);

Le interfacce asincrone (getAppInfo / searchFile / la cinquina media / ocrRecognition) vengono eseguite su thread in background; si noti che in un dato istante è in esecuzione un solo sottoprocesso media; per i task di lunga durata va fornito un punto di annullamento cancelRun().

Riferimento rapido alle interfacce comuni (ulteriori capacità oltre all'esempio) #

Scenario Interfaccia
Leggere/scrivere la propria configurazione getConfig / setConfig (patch a granularità ristretta) / addConfig (aggiunta a un elenco)
Aprire/salvare file browseFile / browseDir / writeFile / readFile (oltre 50MB usare readFileChunk)
Ottenere directory di sistema getKnownDir('download') ecc.
Aprire pagine web/programmi esterni runAny('https://...', '')
Copiare negli appunti navigator.clipboard del front-end (per il testo non serve il nativo)

4. Creare il file di modulo .zenmod (finestra host) #

Creare un nuovo .zenmod in Modules/<categoria>/ (file di esempio: sdk/sample/Modules/SDK_Sample.zenmod):

{
    "id": "sdk_sample",
    "type": "web",
    "name": { "zh_cn": "SDK样例工程", "en": "SDK Sample Project", "...": "共 12 门语言" },
    "desc": { "zh_cn": "基于 MFT 索引的全盘急速文件搜索，支持 Everything 语法", "en": "..." },
    "icon": "fas fa-search",
    "winClassName": "yyzTools::SdkSampleWindowClass",
    "width": 760,
    "height": 540,
    "layoutType": 34,
    "url": "SDK_Sample/index.html",
    "preCreate": 0
}

Descrizione dei campi (tutti i campi letti dal programma principale con type:"web"):

Campo Obbligatorio Descrizione
id sì Unico a livello globale. È anche il nome finestra per windowControl/windowState, l'appId dei tasti di scelta rapidi, l'id di montaggio nel dock
type sì Fisso web
name sì Oggetto a 12 lingue; è ammesso anche il formato stringa pura (consigliato solo per test interni); ordine di risoluzione: lingua corrente → en → stringa pura
desc no Idem
icon no Classe FontAwesome (come sopra) o immagine base64
winClassName no Nome della classe finestra Win32, basta che sia unico a livello globale
width / height no Dimensione iniziale della finestra, predefinita 800x600
layoutType no Maschera di bit del layout di posizione iniziale, 34 = centrato orizzontale + centrato verticale
url sì Percorso della pagina relativo alla radice Web (SDK_Sample/index.html); supporta anche indirizzi online che iniziano con http(s)
preCreate no 1 = pre-crea la finestra all'avvio (accelera la prima apertura), predefinito 0 creazione on-demand
canSuspend no 1 = consente di sospendere la WebView quando la finestra è nascosta per risparmiare risorse (predefinito 1)

Verifica dopo le modifiche: JSON interpretabile, UTF-8 senza BOM, id unico a livello globale, tutte le 12 lingue non vuote.

A questo punto l'app è completa — copiando le due directory come indicato nella sezione 1, è sufficiente cercare "SDK样例工程" oppure "sdk" nel pannello comandi per avviarla (l'indice pinyin viene generato automaticamente); è possibile richiamarla anche con windowControl('sdk_sample', 'show').

5. Testi multilingua (approccio a dizionario) #

La soluzione senza build può usare un normale dizionario come ES module (i18n.js):

const messages = {
    zh_cn: { title: 'SDK样例工程', results: '{{count}} 个结果，耗时 {{ms}} ms', ... },
    en:    { title: 'SDK Sample Project', results: '{{count}} results in {{ms}} ms', ... }
};
export function getMessages(lang) { return messages[lang] || messages.en; }
export function interpolate(dict) {
    return (key, params) => { /* {{count}} → params.count */ };
}

All'inizializzazione si legge getConfig().language per scegliere la lingua, con fallback a en in caso di mancata corrispondenza; le frasi con segnaposto vengono espanse con tf('results', { count, ms }).

Attenzione:

  • I codici lingua usano lo stile minuscolo con underscore (zh_cn), coerente con .zenmod, non BCP47.

  • Il name/desc del .zenmod deve essere completo in tutte le 12 lingue; per i testi all'interno della pagina non ci sono obblighi, l'esempio fornisce solo zh_cn/en, da estendere secondo necessità.

  • Per i moduli che devono seguire immediatamente la lingua dell'interfaccia, si può trasformare il dizionario in file multilingua caricati lazy con import() on-demand, con lo stesso meccanismo di questo documento.

6. Debug e integrazione #

1. Esecuzione diretta senza build (partenza consigliata):
   copiare sdk/sample/Web, sdk/sample/Modules in bin64\ (directory dell'exe Release), riavviare l'exe.
   Dopo aver modificato il front-end, windowControl('sdk_sample','close') e riaprire, oppure riavviare l'exe perché abbia effetto.

2. Esaminare la struttura nel browser:
   fare doppio clic su Web/SDK_Sample/index.html per aprirlo con il browser.
   Nel browser non esiste window.Zen, ZenAPI.call segue il percorso di eccezione restituendo error: -1,
   struttura della pagina / stili / debounce dell'input / logica di rendering sono tutti debuggabili normalmente (tranne le interfacce native).

Suggerimento sulle prestazioni di ricerca: searchFile si appoggia all'indice MFT su tutto il disco lato C++ e in genere restituisce in pochi millisecondi; il nativo ha un meccanismo a slot di ricerca — una nuova richiesta rimpiazza la vecchia non ancora completata (la vecchia restituisce un risultato vuoto); il front-end combina un debounce di 300ms + un numero progressivo per scartare le risposte fuori ordine, così nemmeno la digitazione continua intasa il thread in background o fa sfarfallare risultati vecchi. Le icone dei risultati (base64) sono riportate direttamente da searchFile, senza bisogno di richiamare getFileIcon separatamente.

Se le capacità delle interfacce non bastano (ad esempio serve una nuova funzionalità C++), è possibile inoltrare la richiesta tramite i canali di feedback del sito ufficiale; le interfacce verranno estese dal programma principale nelle versioni successive.

8. Note sulla sicurezza #

Le Native API offrono agli sviluppatori di moduli accesso completo alle capacità di sistema del processo host, inclusi operazioni ad alto rischio come lettura/scrittura ed eliminazione di file, creazione e terminazione di processi, controllo delle finestre, lettura/scrittura degli appunti, modifica delle impostazioni di sistema, esecuzione di comandi da riga di comando, e senza finestre di dialogo per i permessi, senza isolamento sandbox, senza meccanismi di annullamento.

Prima di ogni chiamata valutare autonomamente la sicurezza di ciascuna operazione: validare ogni input esterno, eseguire un backup o chiedere conferma all'utente prima di operazioni irreversibili, e usare solo le capacità davvero necessarie alla funzione. Qualsiasi conseguenza derivante dall'uso è a esclusivo carico dello sviluppatore.
